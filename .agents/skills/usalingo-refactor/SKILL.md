# Usalingo リファクタリング

`apps/ios-swiftui/` のコードを、**外から見た動きを1ミリも変えずに**整理する。

依頼者はエンジニアではない。差分を読んで検算しない。したがってこのスキルの価値は
速さではなく、**嘘をつかないこと**にある。確かめていないことは「確かめていません」と書く。

## 入口

| 呼ばれ方 | やること | 確認を取るか |
|---|---|---|
| 引数なし | **調べるだけ。1文字も書き換えない。** おすすめを効果順に3件出す | 不要 |
| `tidy` | 誰が見ても安全な小掃除を実行し、コミットまでする | 不要 |
| 番号（`2` など）／対象名 | その項目を実行し、コミットまでする | 不要 |
| `undo` | 直前のリファクタリングコミットの戻し方を示す | 実行前に確認 |

引数なしで呼ばれたときは**絶対に書き換えない**。叩き間違えても壊れない入口にする。

## 着手前（毎回。省略しない）

1. `docs/README.md` と `docs/operations/credit-optimization.md` を読む。
2. 他のAIの作業と衝突しないか確かめる。

```bash
git status --short --branch
git worktree list --porcelain
```

3. **ベースラインを取る。** 始める前に緑であることを確認する。

```bash
cd apps/ios-swiftui
xcodebuild -project UsalingoIOS.xcodeproj -scheme UsalingoIOS \
  -destination 'generic/platform=iOS Simulator' -quiet build 2>&1 | grep -E 'error:|warning:' | sort -u
```

- **赤なら整理を始めない。** 先に「なぜ赤か」を報告する。原因が打ち間違いなど明白な破損
  なら直してよいが、それは**バグ修正**であり、リファクタリングとは別のコミットにする。
- 警告の件数を控える。作業後に増えていたら失格とみなす。
- テストの実行先は固定しない。`xcodebuild -showdestinations` か、失敗時のエラーが列挙する
  一覧から、利用可能なシミュレータを選ぶ。

## 調査（引数なしのとき）

効果の大きい順に**3件だけ**出す。それ以上並べない。各件に次を付ける。

- たとえ話1行（専門用語を使わない）
- 対象ファイルと行数
- 危なさ（★★★＝安全、★★☆＝要注意）
- 直したときの減り幅の見込み

探し方の目安。**grepは仮説を立てる道具であり、判決ではない。**

```bash
# 同名の重複定義
grep -rhnE '^\s*(private )?(static )?func [a-zA-Z0-9_]+\(' --include='*.swift' apps/ios-swiftui/UsalingoIOS \
  | sed -E 's/.*func ([a-zA-Z0-9_]+)\(.*/\1/' | sort | uniq -d

# 大きすぎるファイル
find apps/ios-swiftui/UsalingoIOS -name '*.swift' | xargs wc -l | sort -rn | head

# 到達できないかもしれない型（あくまで候補）
grep -rlw --include='*.swift' '<型名>' apps/ios-swiftui/UsalingoIOS apps/ios-swiftui/UsalingoIOSTests
```

**調査結果には賞味期限がある。** 他のAIが同じリポジトリで動いているため、
調べてから実行までに時間が空いたら、**削除・移動の直前に必ず調べ直す**。

## 手口カタログ

ここに無いことはしない。「良さそうだから」で手を広げない。

| 手口 | 中身 | 危なさ |
|---|---|---|
| 重複をまとめる | 同じ処理の2本目を消し、1本を共有する | ★★★ |
| 到達できないコードを消す | どこからも呼ばれていないファイル・型 | ★★☆ |
| 大きすぎるファイルを割る | 別の関心事を別ファイルへ移す | ★★★ |
| 名前を直す | 紛らわしい名前、実態と合わない名前 | ★★★ |
| 散らばった定数を1か所へ | 同じ値の重複定義 | ★★★ |
| ビルド警告を消す | 振る舞いが変わらない範囲だけ | ★★☆ |

★★☆ も実行してよい。ただし**報告に必ず戻し方を書く**。

## 実行

1. 専用branchを作る。`claude/refactor-<短い名前>`。mainへ直接コミットしない。
2. **1コミット1手口。** 混ぜない。戻すときに1つだけ戻せるようにする。
3. 中身の整理と、振る舞いの変更を、同じコミットに入れない。
4. 消す・動かす前に、その型がまだ使われていないか**その場で**調べ直す。
5. 変更後、ビルドとテストを通す。**コンパイラが判決を下す。**
6. **staging はパスを明示する。**

```bash
git add -- <path1> <path2>   # 自分が編集したファイルだけを列挙する
```

- `git add -A`、`git add .`、`git commit -a` を使わない。他のAIの作業を巻き込む。
- コミット直前に、自分が編集したファイル一覧と `git diff --cached --name-only` を
  突き合わせる。1つでも覚えのないファイルがあれば、**コミットせずに報告する**。

## 手を止めて確認を取る場面

ここ以外では確認を取らずに進めてよい。

- push、PR作成、マージ。**これらはこのスキルの範囲外**であり、依頼者の指示がある場合だけ行う。
- ベースラインが赤い。作業後にビルドが通らない、テストが落ちた、警告が増えた。
- 触ろうとしたファイルを、他のセッションが編集している。**その項目は諦め、別の候補に切り替える**。
- 振る舞いを変えないと直せないと分かった。**勝手に変えず、そこで止めて報告する**。
- Notionや外部サービスへの書き込みが必要になった。

## 削ってはいけないもの

`AGENTS.md` の掟が優先する。クレジット節約や行数削減を理由に、次を削らない。

- 入力の検証、エラー処理、セキュリティ、アクセシビリティ、必要なテスト
- 依頼者が明示的に求めたもの

テストが無い場所は、原則として触らない。どうしても必要なら、先にテストを足す。

## 報告

毎回この4つだけを返す。専門用語を使わない。「たぶん大丈夫です」は禁止。

> - **何を直したか** — たとえ話で1行
> - **本当に動くか** — ビルド成功／テスト◯件成功。実行できなかった検証は「未実施」と書く
> - **どれだけ減ったか** — `git show --shortstat` の数字
> - **戻し方** — そのままコピペできるコマンド1行

削除を含むときは、中身の読み出し方も添える。

```bash
git show <コミット>^:<ファイルパス>
```

## やらないこと

- 機能追加、バグ修正、UIの変更、設計の作り直し（リライト）
- 見ていない間に走り続ける自動整理
- 「ついでに良くしておきました」。振る舞いを変えたくなったら止めて報告する
- 一時的な調査結果を、恒久的な文書として `docs/` へ保存すること
