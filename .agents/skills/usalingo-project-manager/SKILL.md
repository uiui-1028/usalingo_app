# Usalingo Project Manager

Usalingoの事実を確認し、子どもでも意味が分かる短い日本語で、実行できる課題へ変換する。

## 最初に読むもの

- Notionへ読み書きする場合は [references/notion-setup.md](references/notion-setup.md) を読む。
- Epic、課題、レポートを作る場合は [references/templates.md](references/templates.md) を読む。

## 依頼を4種類に分ける

1. **洗い出し**: リポジトリとNotionを読み、候補を提示する。まだ登録しない。
2. **登録**: ユーザーがNotion作成を依頼した範囲だけ登録する。
3. **文書作成**: 課題の目的、作業、完了条件、依存関係、根拠を書く。
4. **レポート**: 実際の変更、検証結果、残件を証拠からまとめる。

依頼が「整理して」だけで登録先が明らかな場合は、まず重複を確認してから登録する。大きく範囲が変わる決定だけは、候補を示して確認する。

## 基本運用: 人間は入口、AIは完了まで

- 人間は、AIが示す次の課題候補から「どれに着手するか」を選ぶ。目的、対象外、変えてはいけない条件があれば、この入口で伝える。
- AIは、選ばれた範囲の調査、設計、変更、テスト、レビュー、修正、文書化、完了判定、Notion更新まで担当する。
- 通常の課題では、作業後に人間へ品質レビューを依頼しない。人間の確認待ちを完了条件にしない。
- データ削除、本番DB変更、公開、課金、外部送信など、戻しにくい実行だけは直前に明示的な実行承認を得る。これは品質レビューではなく権限と安全の境界である。
- 人間は途中でいつでも方向を変えられるが、毎回の検品作業を義務にしない。

## 複数AIでチケットを取り合わない

Notionの `status`、`owner`、`blocked_by`、`worker_id`、`lease_until`、`work_branch` を作業権として使う。

1. AIごとにクライアント名を含む一意な `worker_id` を作る。例: `codex-8f31a2`、`claude-a9c204`。別のAIと同じ値を使わない。
2. 次の課題だけを取得候補にする。
   - 実装候補: `status=will`、`owner` が `human` ではない（空欄を含む）、前提課題が完了済み
   - レビュー候補: `status=review`、`owner` が `human` ではなく、有効な作業権がない
3. `status=active` または `review` で、別AIの `lease_until` が現在より後なら、その課題へ触れず別の候補を選ぶ。
4. branchやworktreeを作る前に、予定branch名を決め、`worker_id`、現在から30分後の `lease_until`、予定 `work_branch`、`status=active` を1回の更新でまとめて書く。`lease_until` はタイムゾーン付きISO 8601日時にする。レビュー取得時は `status=review` を保つ。
5. 書き込み直後に同じページを再取得する。`worker_id`、`lease_until`、`work_branch` が自分の予定値と一致しなければ、branch、worktree、差分を作らず撤退する。
6. 作業中は20分以内ごとと、コミット、push、Notion状態変更、外部書き込みの直前に再取得する。担当が変わっていたら、相手の内容を上書きせず停止する。
7. 続行する場合は `lease_until` を現在から30分後へ延長する。待機中のまま期限を延長しない。
8. `done`、`blocked`、`canceled` へ移すときは `lease_until` を空にして作業権を返す。独立したAIへレビューを渡す場合も、`status=review` にして期限を空にする。
9. 期限切れの `active` を引き継ぐ前に、元の `work_branch`、差分、コメントを確認する。確認できない場合は新しい作業を重ねず `blocked` とする。

同じcheckoutまたはworktreeを複数AIで共有しない。異なるチケットでも同じファイルやDB変更を触る場合は同時実行しない。`blocked_by` で順番を付けるか、AIごとの別branch・別worktreeへ分離し、統合前に差分とテストを確認する。

Notionの更新には厳密な同時更新ロックがない。再取得、短い期限、定期確認、Gitの作業分離を組み合わせた協調ロックとして扱い、「絶対に衝突しない」と報告しない。

## 課題を洗い出す

1. `git status --short` で既存変更を確認し、ユーザーの変更を上書きしない。
2. `rg --files` と `rg` を使い、コード、説明書、設定、テストを調べる。
3. Notionの対象プロジェクト、Epic、Taskspaceを検索して取得する。
4. 実装、説明書、Notionの差を次に分ける。
   - 確認済みの問題
   - 決める必要があること
   - まだ情報が足りないこと
   - 将来やりたいこと
5. 1課題を半日から2日で終わる大きさにする。
6. 各課題へ、目的、作業、完了条件、依存関係、確認方法を付ける。

推測を事実として書かない。確認できない項目は `research`、選択が必要な項目は `decision` にする。

## 種類を決める

- `task`: 作れば成果物ができる作業
- `bug`: 期待と実際が違うことを再現できる不具合
- `research`: 情報不足を調べ、答えや比較表を出す作業
- `poc`: 小さく試し、できるか判断する実験
- `idea`: 今は作らない将来案
- `decision`: 選択肢、理由、結論を残す判断

種類を増やさず、上の6種類のどれかを使う。

## Epicを決める

Epicは、複数課題で達成する1つの成果にする。工程名だけにせず、終わったときの価値をタイトルにする。

よい例: `古い説明書を今のSwift版に作り直す`

避ける例: `要件定義フェーズ`、`開発作業`

Epic本文へ、目的、やること、完了のしるし、含めないことを書く。

## 人間が入口を選べるようにする

目的、対象外、AIへ任せる範囲を人間へ白紙から質問しない。リポジトリ、Notion、依頼文を調べたうえで、着手候補を2〜3個提示する。

- 目的候補: 利用者価値、開発・運用成果、リスク低減の視点から出す。
- 今回やらないこと候補: MVPへの集中、後続フェーズへの延期、安全・権限境界の視点から出す。
- AIへ任せる範囲候補: 調査・提案のみ、戻せる変更まで、外部書き込みを含む承認済み範囲の3段階で出す。

各候補へ、選ぶと何が変わるかを1文で添える。おすすめを先頭に置くが、未決定の候補を正式仕様として保存しない。人間が1つまたは複数を選んだ後、重複を整理してEpicまたは課題本文へ反映する。

候補には、利用者・開発への効果、時間の目安、主な危険、先に必要なものを短く付ける。人間が選んだ後は、通常の可逆な作業について追加の確認を挟まず完了まで進める。

## Notionへ登録する

1. 毎回Notion検索を行い、同名の新旧データベースを区別する。
2. 作成前にデータソースを取得し、現在のプロパティ名と選択肢を確認する。
3. 同じEpic名、課題名を検索またはSQL照会し、重複を防ぐ。
4. Epicを先に作り、返されたURLを全課題の `epic` relationへ設定する。
5. 将来候補として作る新規項目は原則 `status=reserved` にする。人間が着手対象へ移したら `status=will` とし、AIが作業権を取得するまでは `will` を保つ。
6. `owner`、`blocked_by`、`source`、`worker_id`、`lease_until`、`work_branch` を現在の事実に基づいて設定する。分からない値を推測で埋めない。
7. 課題本文はテンプレートに従い、チェックできる完了条件を書く。
8. 作成後に再照会し、件数、種類、Epic relation、statusを確認する。

Notionのスキーマを推測しない。取得したスキーマと [references/notion-setup.md](references/notion-setup.md) が違う場合は、取得した現在値を優先し、参照情報が古いと報告する。

## AIレビューを行う

実施とレビューを同じ勢いで済ませず、別の工程として扱う。

1. 実装または文書作成が終わったら `active` から `review` へ移す。`review` は人間の確認待ちではなく、AIが品質確認中であることを表す。
2. 作業者の説明ではなく、依頼文、受け入れ条件、実際の差分、実行ログを先に読む。
3. 次を確認する。
   - 依頼した成果と対象外の境界を守っているか
   - 受け入れ条件を1件ずつ証拠で満たしているか
   - 意図しない変更、古い仕様との矛盾、データや権限の危険がないか
   - 対象テスト、静的確認、必要な動作確認が成功したか
   - 実装済み、テスト済み、本番確認済みを混同していないか
4. 不備を見つけたら人間へ返さず、AIが修正して確認をやり直す。
5. すべて満たしたときだけ `done` とし、確認した証拠、未確認事項、残る危険を完了レポートに残す。
6. 必須の確認環境、権限、外部状態がなく完了できない場合は `done` にせず `blocked` とし、必要な解除条件を書く。判断だけを人間へ丸投げしない。

AIレビューでは「たぶん大丈夫」を合格理由にしない。テストだけでは確認できない仕様は、コード経路、データ構造、画面状態など別の証拠を組み合わせる。

## 文書とレポートを作る

- 調査文書: 調べた対象、確認できた事実、分からないこと、次の判断を書く。
- 決定記録: 選択肢、選んだもの、理由、影響、見直し条件を書く。
- 実施文書: 目的、対象、手順、完了条件、確認方法を書く。
- 完了レポート: 変更、検証、未実施、残件を分ける。
- AIレビューレポート: 受け入れ条件ごとの証拠、見つけて直した不備、未確認事項、完了判定を書く。

「コードを書いた」と「動作確認できた」を分ける。本番操作をしていない場合は、完了したように書かない。

## 守ること

- 現在のSwiftUIアプリは `apps/ios-swiftui/` を基準にし、古いFlutter資料と混ぜない。
- 既存のdirty worktreeはユーザーの作業として保存する。
- 秘密鍵、アクセストークン、個人情報をNotionやレポートへ書かない。
- ユーザーが求めていないコード変更、Supabase変更、削除、公開を行わない。
- 最後に、作ったEpic、課題数、種類、AIレビュー結果、次に選べる2〜3課題を短く伝える。
