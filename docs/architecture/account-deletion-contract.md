# 退会・復元・最終削除のデータ契約

最終決定日: 2026-08-24

対象: SwiftUIアプリ `apps/ios-swiftui/` とSupabase

状態: 設計確定。Edge Function、DB変更、本番設定変更、実データ削除は未実施

## 1. 決めること

利用者が退会した日から365日間はアカウントと利用データを停止状態で保ち、本人確認できた場合だけ復元します。365日を過ぎたら、復元できないよう利用者を特定できるデータを削除します。

この文書は、削除対象、保持対象、匿名化対象、処理順、再試行、監査ログ、失敗時の表示を定めます。実装はUSL-257以降で行います。

## 2. 選択肢

1. 退会日にすべて物理削除する。
2. 365日間停止して復元可能にし、その後に物理削除する。
3. 期限を決めずに保持する。

## 3. 決めたこと

選択肢2を採用します。

1. **退会当日**: ログインを停止し、全端末の更新可能なセッションを失効させる。端末のセッションを消し、通常ログインとデータ閲覧を拒否する。
2. **退会完了から365日間**: 同じ利用者IDのまま、認証情報と利用データを復元専用として保持する。アプリからは利用できない。
3. **365日以内の復元**: 同じメールアドレスを本人確認できた場合だけ、停止した同じ利用者IDを再開する。
4. **365日経過後**: Storageの利用者所有物がないことを確認してから `auth.users` を物理削除し、連鎖する利用者データを削除する。削除後は復元しない。

退会当日に `auth.users` を削除してはいけません。現行構造では `auth.users → public.users → 利用者表` が `ON DELETE CASCADE` でつながるため、365日間の復元ができなくなるからです。

## 4. 現在の保存先の棚卸し

次は、現行SwiftUI、追跡中のmigration、Anki型データモデルを突き合わせた結果です。追跡中のmigrationは増分だけで初期スキーマ全体を再構築できないため、本番適用前に実DBの読み取り監査をもう一度行います。

### 4.1 Supabase Authと利用者テーブル

| 保存先 | 現在入る情報 | 退会当日〜365日 | 365日経過後 | 根拠・注意 |
|---|---|---|---|---|
| `auth.users` | 利用者ID、メール、認証情報・メタデータ | **保持・ログイン停止** | **削除** | 先に消すと子データが連鎖削除される |
| `auth.identities`、`auth.sessions`、refresh token等 | Auth内部の本人確認・セッション情報 | セッションは退会当日に失効。復元に必要な本人識別はAuthの管理下で保持 | `auth.users`削除に伴うAuth管理処理で削除 | Auth管理表をアプリから直接更新しない |
| `public.users` | 利用者ID、メール | **保持** | **連鎖削除** | `auth.users(id)` を参照する利用者データの親 |
| `public.user_profiles` | nickname、plan | **保持** | **連鎖削除** | 現行SwiftUIが読取・更新するプロフィール |
| `public.user_card_progress` | Card単位の復習予定・正誤状態 | **保持** | **連鎖削除** | 現行Anki型の学習記録 |
| `public.user_learning_progress` | 旧word単位の復習予定・正誤状態 | **保持** | **連鎖削除** | 切り戻し用に残る旧表。新旧の二重保持を忘れない |
| `public.user_word_overrides` | 利用者の単語上書き | **保持** | **連鎖削除** | `user_id` は `public.users(id)` 参照 |
| `public.user_word_tags` | 利用者の単語タグ | **保持** | **連鎖削除** | `user_id` は `public.users(id)` 参照 |

現行コード・migrationでは `user_settings` や `user_widget_layouts` を現行サーバー表として利用していません。これらは旧資料だけの名前なので、削除処理へ推測で追加しません。本番実DBに存在する場合は、本番前監査で `user_id`、外部キー、用途を確認し、この表へ追加してから実装します。

### 4.2 端末、Storage、外部サービス

| 保存先 | 現在入る情報 | 退会時の扱い | 根拠・注意 |
|---|---|---|---|
| iOS Keychain | Supabaseのaccess token、refresh token等を含むセッション | 退会完了応答の後に削除。失敗してもサーバー側の停止を取り消さない | `SessionStore.clear()` の対象 |
| iOS UserDefaults | アクセント色、カード角丸など端末内の表示設定 | アプリ初期化時に削除 | 個人学習データではないが、退会後に初期状態へ戻す |
| Supabase Storage `content-images` / `content-audio` | 運営が用意した公式画像・音声 | **保持** | 利用者データではなく公開公式コンテンツ |
| その他のStorage object | 現行コード・migrationでは利用者アップロードを確認できない | 見つかった場合は最終Auth削除より先に削除または所有者解除 | 利用者所有objectがあるとAuthユーザー削除が失敗し得る |
| 外部サービス | 現行iOSコードではSupabase以外への個人データ送信を確認できない | 現在は対象なし | Analytics、広告、Crashlytics、課金、外部メール配信等を追加したら台帳と削除APIをこの契約へ追加する |
| Supabaseバックアップ | DB/Auth/Storageのバックアップ方式・保持期間は本番設定依存 | 通常系の行削除とは別に、期限経過で復元不能になる運用が必要 | 現在値と法的要件は未確認。実装・本番開始前の必須確認 |

## 5. 削除・匿名化・保持の区分

| 区分 | 対象 | 期間 | 理由 | 責任 |
|---|---|---:|---|---|
| 保持 | `auth.users`、`public.users`、プロフィール、新旧学習進捗、単語上書き、タグ、退会監査ログ | 退会完了から365日 | 本人確認後に同じ利用者IDで復元するため | プロダクト責任者が期間を決定。バックエンド担当がアクセス停止と期限を実装 |
| 削除 | 上記の利用者識別可能データ、利用者所有Storage object、端末セッション・設定 | サーバーは365日経過後。端末は退会完了時 | 復元期間終了後は利用目的がなくなるため | バックエンド・運用担当 |
| 匿名化 | 利用者ID、メール、request IDへ戻せない集計値だけ | 必要な場合のみ期限なし | 品質・件数の傾向を個人と結び付けず確認するため | プロダクト責任者。再識別可能なら匿名化ではなく削除 |
| 保持判断待ち | バックアップ、プロバイダー内部ログ、法令上の保存が必要な記録 | **未確定** | 契約・本番設定・法務判断が未確認 | 法務・プライバシー責任者を実装前に指名して確定 |

IPアドレス、メール、nickname、自由入力タグは匿名化済みとは扱いません。salt付きhashや暗号化だけで元の利用者へ戻せる場合も、匿名化ではなく個人データとして扱います。

## 6. サーバー処理の順序

### 6.1 退会当日

1. 有効なJWTから対象利用者IDを取得し、現在のパスワード再入力と「退会」の文字入力を確認する。クライアントから任意の対象IDを受け取らない。
2. 一意な退会request IDで処理を開始し、同じrequest IDの再送は同じ結果を返す。
3. サーバー側の退会状態へ `disabled_at`、`restorable_until = disabled_at + 365日`、処理状態を保存する。状態保存用の非公開テーブルはUSL-257で設計・migration・RLS/GRANT検証を行う。
4. 全端末のrefresh tokenを失効させる。既発行access tokenは期限まで有効になり得るため、退会状態の利用者をData APIと機密処理で拒否する経路も必要とする。
5. ログインを拒否する。実装に使うSupabase Auth管理APIと復元方法は、USL-257で現在の公式仕様とローカル環境を使って確認する。
6. 利用者データは物理削除せず、通常のアプリ経路から読取・更新できないことを確認する。
7. クライアントへ退会完了を返す。クライアントはKeychainセッションとUserDefaults設定を消し、初期画面へ戻す。

### 6.2 365日以内の復元

1. 同じメールアドレスを、メール確認と再認証で本人確認する。
2. `restorable_until` 以内で、最終削除が始まっていないことを確認する。
3. 停止した同じ `auth.users.id` を再開する。別の利用者IDを作ってデータを付け替えない。
4. 新しいセッションを発行し、プロフィール・学習進捗・上書き・タグが同じIDで読めることを確認する。
5. 復元完了の監査イベントを残す。

### 6.3 365日経過後の最終削除

1. `restorable_until < now()`、停止中、復元・削除処理が未進行である対象だけを管理側でロックする。
2. 利用者所有のStorage objectと、将来追加された外部サービスを列挙し、削除結果を確認する。公式コンテンツbucketは削除しない。
3. 退会監査ログのうち個人へ戻せる行を削除対象へ含める。残す場合は再識別不能な集計値だけにする。
4. サーバー管理APIで `auth.users` を削除する。`public.users` と全子表は外部キーの連鎖削除に任せるが、実装テストで件数0を確認する。
5. Auth内部のidentity・session・token、`public.users`、全 `user_id` 表、利用者所有Storage object、外部サービスの残件が0であることを確認する。
6. バックアップが契約上の保持期間を過ぎて復元不能になる時点は、通常DBとは別の運用記録で追跡する。

## 7. 部分失敗、再実行、冪等性

- 状態は最低でも `requested`、`disabled`、`purging`、`purged`、`restore_requested`、`restored`、`failed` を区別する。
- 退会request IDを一意制約にし、同じ要求を複数回受けても保持期限を延ばしたり別ユーザーを作ったりしない。
- 各外部処理は「対象がすでにない」を成功として扱い、完了したstepを保存して未完了stepから再開する。
- 最終削除は対象行をロックして多重実行を防ぐ。`purged` 後の再実行は成功済み結果を返す。
- セッション失効後にDB更新が失敗した場合も、ログインを再開しない。利用者には退会手続き中と表示し、管理側で再試行する。
- Storageまたは外部サービス削除が失敗した場合は `auth.users` を先に消さず、`failed` と失敗stepだけを記録して再試行する。
- 最終削除の一部が終わった後はロールバックで個人データを復元しない。残りを安全に削除する方向で再試行する。
- 自動再試行は指数バックオフと上限回数を設け、上限後は運用アラートへ送る。無限ループにしない。

## 8. 監査ログ契約

記録してよい情報:

- 退会request ID、対象の内部user ID
- `requested_at`、`disabled_at`、`restorable_until`、`purged_at`
- 状態、step名、試行回数、成功・失敗、再試行予定時刻
- 秘密を含まないエラー分類と追跡用correlation ID

記録してはいけない情報:

- パスワード、access token、refresh token、JWT、再認証コード
- リクエスト・レスポンス本文の丸ごと保存
- メール、nickname、自由入力タグ、学習内容、Storage object本文
- `service_role` key、秘密鍵、認証header

監査ログも利用者へ結び付く間は個人データです。退会完了から365日で削除し、必要なら個人へ戻せない成功率・件数だけを集計として残します。

## 9. 利用者へ表示する結果

| 状態 | 表示 | アプリの動き |
|---|---|---|
| 退会完了 | 「退会手続きが完了しました。365日以内は本人確認後に復元できます。」 | Keychainと端末設定を消して初期画面へ戻す |
| 同じrequestの再送 | 「退会手続きはすでに受け付けています。」 | 保存済み状態を表示し、重複処理しない |
| 一時失敗・状態保存済み | 「退会手続きを続けています。ログインは停止されています。」 | パスワードや内部エラーを表示せず、管理側で再試行 |
| 受付前の本人確認失敗 | 「本人確認ができませんでした。もう一度お試しください。」 | 退会状態へ変えない |
| 復元期限切れ | 「復元できる期間を過ぎています。」 | 新規登録とは分け、削除状態を確認する |

「すべて削除済み」と表示するのは、最終削除の検証が終わった後だけです。バックアップの保持終了が別日なら、その違いをプライバシー表示へ反映します。

## 10. 責任分担と未確認事項

| 判断・作業 | 責任 |
|---|---|
| 365日保持、同一ID復元、365日後の最終削除という製品判断 | プロダクト責任者（確定済み） |
| Edge Function、非公開状態表、Auth停止・復元、RLS/GRANT、削除job、監視 | バックエンド・運用担当（USL-257以降） |
| アプリの再認証、退会確認、端末初期化、利用者表示 | iOS担当（USL-259） |
| バックアップ、Supabase内部ログ、外部サービス契約、法的根拠・保持期間 | **法務・プライバシー責任者を実装前に指名して確認** |
| 本番設定変更・実利用者への適用・実データ削除 | 対象と影響を示した別の明示承認が必要 |

法務未確認事項は、この文書からAIが断定しません。次を本番実装前の停止条件にします。

- Supabaseの本番バックアップ、PITR、Auth・API・Edge Functionログ、Storageの実保持期間
- 利用国・地域ごとの削除請求、会計・不正対策・紛争対応に必要な保持根拠
- 委託先・メール配信・監視・分析サービスを追加する場合の削除APIと契約上の削除期限
- プライバシーポリシー、App Store ConnectのApp Privacy、アプリ内説明との一致

## 11. 理由

- 利用者が決めた365日の復元期間と、同じ学習履歴を戻す要件を両立できる。
- `ON DELETE CASCADE` を使った現行の外部キー構造と矛盾しない。
- SupabaseではAuthユーザー削除だけでは既発行JWTが即時無効にならず、Storage所有objectが削除を妨げる場合があるため、セッション失効、停止状態、Storage先行確認を別stepにできる。
- 旧退会案にある退会当日の全削除や旧テーブル名を、現行Anki型データへ誤適用しない。

## 12. 影響する場所

- `supabase/migrations/`: 非公開の退会状態・監査表、権限、期限処理
- `supabase/functions/`: 退会受付、復元、最終削除の管理処理
- `apps/ios-swiftui/`: 再認証、退会確認、端末初期化、状態表示
- `docs/architecture/anki-data-model.md`: 新旧学習進捗の保持・削除境界
- プライバシーポリシー、App Store ConnectのApp Privacy

## 13. 見直す条件

- 保持期間を変更する人間の決定があったとき
- 新しい `user_id` 表、利用者アップロード、外部サービス、分析・課金・メール配信を追加するとき
- Supabase Authの停止・復元・セッション失効仕様、Storage所有権、バックアップ契約が変わったとき
- 利用国・地域、法的根拠、App Store要件が変わったとき
- 本番実DB監査で、この棚卸しにない利用者データを発見したとき

## 14. 実装前の確認方法

1. `auth.users` を起点に、全外部キーと全 `user_id` / owner列を本番読み取りで再棚卸しする。
2. Storage bucket、object owner、RLS policy、外部サービス台帳を照合する。
3. ローカルSupabaseで利用者A・Bを作り、Aの退会でBと公式コンテンツが残ることを確認する。
4. 退会の二重送信、各stepの人工失敗、再試行、365日境界、復元と最終削除の競合をテストする。
5. 最終削除後にAuth、全利用者表、Storage、監査ログの個人行が0件であることを確認する。
6. 本番変更と実データ削除は、別の明示承認後にだけ行う。
