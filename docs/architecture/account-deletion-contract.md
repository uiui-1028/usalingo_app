# 退会・復元・最終削除のデータ契約

最終決定日: 2026-09-04（2026-08-24の決定を改定）

対象: SwiftUIアプリ `apps/ios-swiftui/` とSupabase

状態: 設計確定。Edge Functionは実装済みだが**本番未デプロイ**。本番設定変更、実データ削除は未実施

## 1. 決めること

利用者が退会したその場で、アカウントと利用データをすべて削除します。停止期間も復元も設けません。

この文書は、削除対象、処理順、失敗時の扱い、失敗時の表示を定めます。

## 2. 選択肢

1. 退会日にすべて物理削除する。
2. 365日間停止して復元可能にし、その後に物理削除する。
3. 期限を決めずに保持する。

## 3. 決めたこと

**選択肢1を採用します（2026-09-04 改定。旧決定は選択肢2でした）。**

1. **本人確認**: 退会の直前にパスワードを再確認する。盗まれた端末からの退会を防ぐため。
2. **Storageの所有物を削除**: 利用者が所有するobjectを先に消す。残っているとAuthの利用者削除が失敗し得る。
3. **`auth.users` を削除**: `auth.users → public.users → 利用者表` の `ON DELETE CASCADE` により、利用者データが連鎖して消える。
4. **端末を初期化**: セッションと端末内設定を消す。

### なぜ改定したか

365日の停止期間は、それ自体より**周辺の仕組みを大量に必要とする**ことが問題でした。

- 「停止中だがデータは在る」利用者をアプリから締め出すため、利用者表6つへ restrictive ポリシーと `is_current_user_active()` が必要
- 停止→最終削除の途中経過を追うため、状態機械（`private.account_deletions`）と再試行の記録、RPC4本が必要
- これらは本番へ一度も適用されないまま、後続作業（G-4の学習記録バックアップ）の前提を塞いでいた

即時削除ならこれらは**すべて不要**です。DBに退会専用のテーブル・関数・ポリシーは1つも要りません。

### 引き換えに諦めること

**誤操作からの復旧ができません。** 退会を押し間違えた利用者のデータは戻せません。
これを、確認テキスト「退会」の入力・チェックボックス・パスワード再確認の3段で防ぎます。

## 4. 現在の保存先の棚卸し

次は、現行SwiftUI、追跡中のmigration、Anki型データモデルを突き合わせた結果です。追跡中のmigrationは増分だけで初期スキーマ全体を再構築できないため、本番適用前に実DBの読み取り監査をもう一度行います。

### 4.1 Supabase Authと利用者テーブル

| 保存先 | 現在入る情報 | 退会時 | 根拠・注意 |
|---|---|---|---|
| `auth.users` | 利用者ID、メール、認証情報・メタデータ | **退会時に削除** | これを消すと子データが連鎖削除される |
| `auth.identities`、`auth.sessions`、refresh token等 | Auth内部の本人確認・セッション情報 |`auth.users`削除に伴うAuth管理処理で削除 | Auth管理表をアプリから直接更新しない |
| `public.users` | 利用者ID、メール | **連鎖削除** | `auth.users(id)` を参照する利用者データの親 |
| `public.user_profiles` | nickname、plan | **連鎖削除** | 現行SwiftUIが読取・更新するプロフィール |
| `public.user_card_progress` | Card単位の復習予定・正誤状態 | **連鎖削除** | 現行Anki型の学習記録 |
| `public.user_learning_progress` | 旧word単位の復習予定・正誤状態 | **連鎖削除** | 切り戻し用に残る旧表。新旧の二重保持を忘れない |
| `public.user_word_overrides` | 利用者の単語上書き | **連鎖削除** | `user_id` は `public.users(id)` 参照 |
| `public.user_word_tags` | 利用者の単語タグ | **連鎖削除** | `user_id` は `public.users(id)` 参照 |
| `public.user_local_study_backups` | 端末の学習記録のバックアップ1件 | **連鎖削除** | `user_id` は `public.users(id)` 参照（G-3） |

現行コード・migrationでは `user_settings` や `user_widget_layouts` を現行サーバー表として利用していません。これらは旧資料だけの名前なので、削除処理へ推測で追加しません。本番実DBに存在する場合は、本番前監査で `user_id`、外部キー、用途を確認し、この表へ追加してから実装します。

### 4.2 端末、Storage、外部サービス

| 保存先 | 現在入る情報 | 退会時の扱い | 根拠・注意 |
|---|---|---|---|
| iOS Keychain | Supabaseのaccess token、refresh token等を含むセッション | 削除完了応答の後に消す。失敗してもサーバー側の削除は取り消さない | `SessionStore.clear()` の対象 |
| iOS UserDefaults | アクセント色、カード角丸など端末内の表示設定 | アプリ初期化時に削除 | 個人学習データではないが、退会後に初期状態へ戻す |
| Supabase Storage `content-images` / `content-audio` | 運営が用意した公式画像・音声 | **保持** | 利用者データではなく公開公式コンテンツ |
| その他のStorage object | 現行コード・migrationでは利用者アップロードを確認できない | 見つかった場合は最終Auth削除より先に削除または所有者解除 | 利用者所有objectがあるとAuthユーザー削除が失敗し得る |
| 外部サービス | 現行iOSコードではSupabase以外への個人データ送信を確認できない | 現在は対象なし | Analytics、広告、Crashlytics、課金、外部メール配信等を追加したら台帳と削除APIをこの契約へ追加する |
| Supabaseバックアップ | DB/Auth/Storageのバックアップ方式・保持期間は本番設定依存 | 通常系の行削除とは別に、期限経過で復元不能になる運用が必要 | 現在値と法的要件は未確認。実装・本番開始前の必須確認 |

## 5. サーバー処理の順序

1. 有効なJWTから対象利用者IDを取得し、現在のパスワード再入力と「退会」の文字入力を確認する。クライアントから任意の対象IDを受け取らない。
2. 利用者が所有するStorage objectを削除する。公式コンテンツbucketは削除しない。
3. サーバー管理APIで `auth.users` を削除する。`public.users` と全子表は外部キーの連鎖削除に任せる。
4. クライアントへ削除完了を返す。クライアントはKeychainセッションとUserDefaults設定を消し、初期画面へ戻す。

停止状態を持たないため、途中経過を記録する非公開テーブルもRPCも要りません。
DBに退会専用のオブジェクトは**1つも作りません**。

## 6. 部分失敗の扱い

途中で失敗したときは、状態を残さずエラーを返します。利用者はそのまま**もう一度実行するだけ**です。

- Storage削除に失敗したら `auth.users` は消さない。何も消えていない状態で終わる
- `auth.users` 削除に失敗したら、Storageだけ消えた状態で終わる。再実行で続きが完了する
- 各処理は「対象がすでにない」を成功として扱う
- 削除が完了した後の再実行は、セッションが無効になっているため `unauthorized` で終わる

再試行のバックオフ、状態機械、管理側のアラートは要りません。利用者の再実行が唯一の再試行経路です。

## 7. 記録してよい情報

このアプリは退会の監査ログを残しません。利用者に結び付くため、残せば削除対象が増えるだけです。
Edge Functionの `console.error` へ出すのは、秘密を含まない固定のエラー分類だけとします。

記録してはいけない情報:

- パスワード、access token、refresh token、JWT
- リクエスト・レスポンス本文の丸ごと保存
- メール、nickname、自由入力タグ、学習内容、Storage object本文
- `service_role` key、秘密鍵、認証header

## 8. 利用者へ表示する結果

| 状態 | 表示 | アプリの動き |
|---|---|---|
| 削除完了 | 「アカウントと学習記録を削除しました。この操作は取り消せません。」 | Keychainと端末設定を消して初期画面へ戻す |
| 本人確認失敗 | 「本人確認ができませんでした。パスワードを確認してください。」 | 何も削除しない |
| 途中で失敗 | 「削除の途中で問題が起きました。もう一度お試しください。」 | 内部エラーを表示せず、再実行を促す |
| セッション切れ | 「セッションの期限が切れています。もう一度Sign Inしてください。」 | 何も削除しない |

## 10. 理由

- 停止期間を持たないため、`is_current_user_active()` と利用者表6つへの restrictive ポリシー、
  状態機械、RPC群が丸ごと不要になる。DBの変更点がゼロになる。
- `ON DELETE CASCADE` を使った現行の外部キー構造にそのまま乗る。
- 失敗時は「何も記録せず、利用者が再実行する」だけで済み、再試行の仕組みを持たなくてよい。

## 11. 影響する場所

- `supabase/functions/delete-user-account/`: 本人確認、Storage削除、Auth削除
- `apps/ios-swiftui/`: 再認証、退会確認、端末初期化、状態表示
- プライバシーポリシー、App Store ConnectのApp Privacy

## 12. 見直す条件

- 復元期間を設ける人間の決定があったとき（そのときは本文書の選択肢2へ戻す）
- 新しい `user_id` 表、利用者アップロード、外部サービス、分析・課金・メール配信を追加するとき
- Supabase Authのユーザー削除・Storage所有権の仕様が変わったとき
- 利用国・地域、法的根拠、App Store要件が変わったとき

## 13. 実装前の確認方法

1. `auth.users` を起点に、全外部キーと全 `user_id` / owner列を本番読み取りで再棚卸しする。
2. ローカルSupabaseで利用者A・Bを作り、Aの退会でBと公式コンテンツが残ることを確認する。
3. 連鎖削除で全利用者表の行が0件になることを確認する（`supabase/tests/usl_257_account_deletion.test.sql`）。
4. 本人確認失敗・途中失敗・再実行を確認する（`supabase/functions/delete-user-account/core_test.ts`）。
5. 本番変更と実データ削除は、別の明示承認後にだけ行う。
