# Usalingo ワークフロー設計 実行計画書

## 目的

競合アプリを参考に、Usalingoの使い方と動きを決めます。

次の順番で進めます。

```text
競合を比べる
→ 最も短い成功の流れを決める
→ MVPに必要な分かれ道を決める
→ 表側の部品に分ける
→ 裏側の状態と動きに分ける
```

Swift、データベース、APIなど、作り方の話は入れません。どの開発言語でも使える形にします。

## 言葉の意味

この計画では、次の意味で言葉を使います。

- **表側（ホワイトボックス）**：利用者に見える画面、言葉、ボタン、反応。
- **裏側（ブラックボックス）**：利用者には見えない状態、判定、保存、次の動き。
- **状態**：その時、アプリがどうなっているか。
- **出来事**：タップ、回答、完了など、状態を変えるきっかけ。
- **分かれ道**：条件によって、次の動きが変わる場所。

一般的にはホワイトボックスとブラックボックスを別の意味で使う場合があります。そのため、完成する文書では「表側」と「裏側の状態」を正式な名前にします。

## 最後に作るもの

| 成果物 | 内容 |
|---|---|
| 競合比較表 | 各アプリの手順、良い点、邪魔な点 |
| 最短成功フロー | Usalingoで最も大切な一本の流れ |
| MVP分岐表 | 最初から必要な分かれ道と失敗時の動き |
| 表側一覧 | 利用者に見える画面と操作 |
| 裏側状態図 | 状態、出来事、判定、保存、次の状態 |

作業中の記録と決定は [`workflow-records/`](workflow-records/README.md) に残します。この実行計画書は進め方を定める文書であり、未記入の例や仮説は確定仕様として扱いません。

## 人間とAIの役割

### 人間がすること

- AIのWeb調査では分からない重要な点だけ、必要に応じて短く実機確認する。
- AIが出した2〜3案から、Usalingoに合うものを選ぶ。
- 最も大切な体験を最終決定する。

### AIがすること

- 記録用の型を用意する。
- 公式サイト、公式ヘルプ、ストア情報から競合の事実を先に調べる。
- Webで確認できないことを推測で埋めず、仮説と未確認へ分ける。
- 必要な実機確認を少数の質問へ絞る。
- 競合の共通点と違いを見つける。
- 最短成功フローを2〜3案作る。
- MVPの分かれ道を整理する。
- 表側と裏側の状態をつなぐ。
- 抜け、矛盾、重複を確認して直す。

## 進め方

### 1. 競合を同じ条件で比べる

最初は次の4つを比べます。

1. Anki：復習ルールと自由さ
2. Quizlet：カード操作
3. TANZAM：イラストの見せ方
4. mikan：学習開始までの短さ

足りない視点が出たときだけ、ほかの競合を追加します。

- Drops・Langaku：楽しさ
- Duolingo・Epop：続けたくなる流れ
- WordHolic：カードの自由さ
- abceed：教材を探して学ぶ流れ

#### 最初にAIがWebで確認すること

- 学習を始めるまでに必要な選択
- 問題、回答、評価、次の問題の流れ
- 自動復習、学習モード、進捗保存の説明
- イラスト、例文、音声の見せ方
- Web情報だけでは確認できないこと

公式情報と、そこから考えた仮説を分けます。価格、画面、機能は変わるため、確認日と出典を記録します。

#### 必要な場合だけ実機で確認すること

Webでは判断できず、Usalingoの決定を変える点だけを次の流れで確かめます。

```text
初めて開く
→ 最初の学習を始める
→ 5問答える
→ 学習を終える
→ もう一度開く
```

ゲストから登録できる場合は、記録がどう扱われるかも確認します。

#### 記録する型

```text
アプリ名：
今いる場所：
したこと：
次に出たもの：
選ばされたこと：
タップ数：
情報源：
確認できた事実：
Webから考えた仮説：
未確認：
人が確かめるなら何を見るか：
```

#### 終わりのしるし

- 4つのアプリについて、公式Web情報から比較に必要な事実を記録した。
- 事実、仮説、未確認を分けて記録した。
- 人が確認する項目を、ワークフロー決定に影響するものだけへ絞った。
- 分からなかった所を、分かったふりで埋めていない。

### 2. 競合からパターンを見つける

AIが記録を次の4つに分けます。

- どのアプリにもある動き
- 学習開始を早くする動き
- 「分かった！」を生む動き
- 邪魔な選択や画面移動

AIは、似た動きを一つにまとめます。人間は、残したい体験と消したい体験を決めます。

#### 終わりのしるし

- 採用候補と不採用候補に理由がある。
- 競合の見た目を、そのままコピーしていない。
- Usalingoの強みであるイラスト、データ、使い心地につながっている。

### 3. 最短成功フローを決める

最も大切な成功を、一文にします。

最初の仮説は次です。

> アプリを開いた人が、迷わずイラスト付き英単語に答え、「分かった！」を感じ、そのまま次の問題へ進める。

AIは、この成功に届く最短フローを2〜3案作ります。各案は次の型で書きます。

```text
今の状態
→ 利用者がすること
→ 表側の反応
→ 裏側で決まること
→ 次の状態
```

各手順について「なくしても成功できるか」を確認します。なくせる手順は外します。

#### 終わりのしるし

- 最短成功フローが一本に決まった。
- 利用者へ、復習か新しい問題かを選ばせない。
- 学習を始める前の不要な説明や設定がない。
- 一つひとつの手順に必要な理由がある。

### 4. MVPの分かれ道を決める

最短成功フローだけでは扱えない場合を追加します。

最初は次だけを対象にします。

- 初めて使う／いつも使っている
- ゲスト／登録済み
- 答える前／答えた後
- 記録できた／記録できなかった
- 学習を続ける／終える
- ゲスト記録を引き継げた／引き継げなかった
- 学習できるカードとイラストがそろっている／いない

各分かれ道は次の型で書きます。

```text
条件：
進む先：
利用者に見せること：
守るデータ：
失敗したとき：
戻る場所：
```

#### MVPへ入れる基準

次のどれかに当てはまる分かれ道だけを入れます。

- 学習を始められなくなる。
- 学習を続けられなくなる。
- 学習記録を失う。
- ゲストの記録を引き継げない。
- 間違ったカードや結果を見せる。

### 5. 表側を部品に分ける

見た目をデザインする前に、必要な表側だけを並べます。

候補は次です。

- 学習を始める場所
- 問題を見せる場所
- 答えを見せる場所
- 正解・不正解を伝える反応
- 次へ進む操作
- 学習終了の案内
- アカウント作成の案内
- 失敗とやり直しの案内

各部品は次の型で書きます。

```text
名前：
目的：
見せる情報：
一番大切な操作：
利用者に分かってほしいこと：
入る条件：
出る条件：
```

色、形、文字サイズ、Swiftの画面名などは決めません。

### 6. 裏側を状態と動きに分ける

裏側は、処理の名前ではなく、状態の変化として書きます。

学習の基本状態は次の形から始めます。

```text
まだ始めていない
→ 学習できる
→ 問題を見せている
→ 回答を受け取った
→ 結果が決まった
→ 次に学ぶ時が決まった
→ 記録できた
→ 次の問題 または 学習終了
```

アカウントの基本状態は次です。

```text
ゲスト
→ 登録中
→ 登録済み
→ 記録を引き継いでいる
→ 引き継ぎ済み
```

各状態は次の型で書きます。

```text
状態の名前：
この状態になる条件：
受け取れる出来事：
変えてよいもの：
必ず守るもの：
次の状態：
失敗したときの状態：
もう一度試したときの動き：
```

#### 必ず守ること

- 一つの回答から、学習結果を二重に作らない。
- 記録できていない回答を、記録済みとして見せない。
- アカウント登録で、ゲストの学習記録を失わない。
- 同じ操作をもう一度しても、記録が壊れない。
- 英単語、意味、イラスト、例文、音声の組み合わせを間違えない。
- 次の問題は、Ankiの復習ルールで自動決定する。
- 利用者へ、裏側の判断をさせない。

### 7. 表側と裏側をつなぐ

最後に、一つの表へまとめます。

| 表側 | 利用者の操作 | 裏側の状態 | 起きる出来事 | 次の状態 |
|---|---|---|---|---|
| 問題 | 答えを見る | 問題を見せている | 回答を開く | 回答を受け取れる |
| 回答 | 正誤を伝える | 回答を受け取った | 評価する | 結果が決まった |
| 次へ | 次の問題へ進む | 記録できた | 次を求める | 次の問題／終了 |

この表は例です。実際の内容は、競合比較と最短成功フローの決定後に作ります。

## AIと人間の進行方法

各段階で、次のやり取りを1回ずつ行います。

1. AIがWeb調査を行い、事実、仮説、未確認に分ける。
2. 必要な場合だけ、人間が短い実機確認や感想を渡す。
3. AIが、おすすめを先頭にして2〜3案を出す。
4. 人間が、採用する案を選ぶ。
5. AIが、決定を文書へ反映する。
6. AIが、矛盾と抜けを確認して次へ進む。

人間へ毎回ゼロから質問しません。AIが材料から候補を作り、人間は大切な入口だけを選びます。

## 作業の目安

| 段階 | 人間 | AI |
|---|---:|---:|
| 競合4アプリの確認 | 必要なら20〜40分 | Web調査と仮説作成 60〜90分 |
| パターン整理 | 15分確認 | 30〜60分 |
| 最短成功フロー | 30分選択 | 30〜60分 |
| MVP分岐 | 30分選択 | 60〜90分 |
| 表側・裏側の整理 | 30分確認 | 90〜120分 |
| 最終確認 | 15分決定 | 30〜60分 |

人間の作業は、選択と重要な実機確認を合わせて1〜2時間以内を目安にします。競合を追加しても、まずAIがWebで調べ、人間の作業を自動では増やしません。

## 完了のしるし

- 最短成功フローが一本ある。
- MVPの分かれ道がすべて最短成功フローにつながる。
- 表側の各部品に、対応する裏側の状態がある。
- すべての状態に、入る条件と出る条件がある。
- 失敗したとき、戻る場所が決まっている。
- ゲストの学習記録が失われない。
- 特定の開発言語に依存する言葉がない。
- 決定、候補、未確認が分けて書かれている。
