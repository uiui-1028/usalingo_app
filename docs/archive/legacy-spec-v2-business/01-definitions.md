## ***【 usalingo_00_03｜開発方針 】***

*本セクションでは、usalingoの開発を導く基本原則と方法論を定義する。これにより、品質、効率性、そしてプロジェクトの成功確度を最大化する。*

---

### **● 行動哲学｜ひとりユニコーン**

本プロジェクトは、単独の個人が最新の技術、特にAIとの協働（バイブコーディング）を最大限に活用し、大規模なチームに匹敵する価値を創出する「ひとりユニコーン」を目指す試みである。この思想に基づき、**意思決定の速度**と**実行の柔軟性**を最優先する。完璧な計画よりも、**迅速な仮説検証と反復的な改善**を重視し、常にプロダクトの本質的な価値向上に集中する。

---

### **● 開発手法｜アジャイル開発**

固定的な長期計画に固執せず、短いサイクル（スプリント）で「計画 → 設計 → 実装 → テスト」を繰り返すアジャイル開発のアプローチを採用する。

```yaml
--------------------------------
WORKFROW: "アジャイル開発"
name: アジャイル開発 (Agile Development)
description: "短い開発サイクル（スプリント）を反復することで、変化に柔軟に対応し、プロダクトの価値を最大化するための開発アプローチ。"
tool: "Notion (Workspace, Taskspace)"
workflow:
--------------------------------
- step: 1. エピックの定義 (Epic Definition)
  details: "実現したい大きな機能や価値を「エピック」として `Pro｜usalingo｜01｜Workspace` データベースに定義する。"
--------------------------------
- step: 2. タスクへの分解 (Task Breakdown)
  details: "エピックを達成するために必要な、具体的かつ数日で完了可能な作業単位（タスク）に分解し、`Pro｜usalingo｜02｜Taskspace` データベースで管理する。"
--------------------------------
- step: 3. 実装とテスト (Implementation & Testing)
  details: "ユーザー価値が最も高いと判断されたタスクから優先的に実装し、即座にテストを行う。"
--------------------------------
- step: 4. 自己レビューと改善 (Self-Review & Improvement)
  details: "開発者自身が最初のユーザーとして実装された機能を評価し、得られたフィードバックや新たな発見を次のサイクルのエピックやタスクに反映させる。このサイクルを継続的に繰り返す。"
```

---

### **● 設計思想｜クリーンアーキテクチャ**

アプリケーションのメンテナンス性と拡張性を長期的に担保するため、クリーンアーキテクチャの設計思想を導入する。これにより、UI、ビジネスロジック、データソースといった各要素の独立性を高め、将来的な仕様変更や技術刷新に強い構造を構築する。

```bash
-------------------------------
WORKFROW: "クリーンアーキテクチャ"
name: クリーンアーキテクチャ (Clean Architecture)
description: "UI・ビジネスロジック・データを厳密に分離し、変更に強くテストしやすいコード構造を維持するための設計規則。"
tool: "Flutter, Dart, Riverpod"
workflow:
--------------------------------
- principle: "依存関係のルール (The Dependency Rule)" details: "全ての依存関係は、外側から内側（プレゼンテーション層 → ドメイン層 ← データ層）に向かう。これにより、アプリの核となるビジネスロジック（ドメイン層）が、UIやデータベースといった外部要因から完全に独立する。"
--------------------------------
- step: 1. ドメイン層の定義 (Domain Layer Definition) details: "最初に、アプリケーションの核となるビジネスルールやデータ構造（エンティティ）、そしてその操作（ユースケース、リポジトリのインターフェース）を定義する。この層は他のどの層にも依存しない。"
--------------------------------
- step: 2. データ層の実装 (Data Layer Implementation) details: "ドメイン層で定義されたインターフェースに基づき、SupabaseやローカルDB（SQLite）からデータを取得・保存するための具体的な処理（リポジトリの実装）を記述する。"
--------------------------------
- step: 3. プレゼンテーション層の実装 (Presentation Layer Implementation) details: "最後に、ユーザーが見て操作するUIを構築する。この層はドメイン層のユースケースを呼び出すことでビジネスロジックを実行し、結果を画面に表示する。"
```

### **● 設計思想｜オブジェクト指向**

アプリケーションの複雑さを管理し、コードの再利用性と保守性を高めるため、オブジェクト指向プログラミング（OOP）を基本原則として採用する。これにより、現実世界の概念（例：「単語」「学習デッキ」「ユーザー」）を、データと振る舞いを併せ持つ「オブジェクト」としてモデル化し、

```bash
--------------------------------
WORKFROW: "オブジェクト指向プログラミング"
name: オブジェクト指向 (Object-Oriented Programming)
description: "データとそれを操作する手続きを一つの「オブジェクト」としてまとめることで、ソフトウェアを部品の組み合わせとして設計するプログラミング手法。"
tool: "Dart"
workflow:
--------------------------------
- principle: "カプセル化 (Encapsulation)"
  details: "関連するデータ（プロパティ）とロジック（メソッド）を一つのクラスに集約し、内部構造を隠蔽する。例えば、`LearningDeck` オブジェクトは自身の単語リストと学習進捗を内部で管理し、外部には『学習を開始する』『単語を追加する』といった安全な操作のみを公開する。"
--------------------------------
- principle: "ポリモーフィズム (Polymorphism)"
  details: "異なるクラスのオブジェクトを、共通のインターフェースを通じて同じように扱えるようにする。例えば、`学習デッキブロック`や`ストリークブロック`を、UI上では全て共通の `Block` 型として扱い、描画や更新処理を統一的に行う。これにより、新しい種類のブロックを簡単に追加できるようになる。"
--------------------------------
- principle: "責務の分離 (Separation of Concerns)"
  details: "各オブジェクトが持つ責務を単一かつ明確に定義する。これにより、コードの独立性が高まり、変更時の影響範囲を限定できる。クリーンアーキテクチャにおける`Entity`や`Model`は、この原則に基づいて設計される。"
```

### **● 設計手法｜ワイヤーフレーム駆動開発**

本プロジェクトのフロントエンド開発は、「ワイヤーフレーム駆動開発」を基本方針とする。UIの骨格（ワイヤーフレーム）を先行して実装し、ビジネスロジックや詳細なデザインは後から統合することで、開発プロセスを効率化し、手戻りを最小限に抑えることを目的とする。

```yaml
--------------------------------
WORKFROW: "ワイヤーフレーム駆動開発"
name: ワイヤーフレーム駆動開発 (Wireframe-Driven Development)
description: UIの構造とロジックを分離し、UIの骨格から開発を始めることで、手戻りを防ぎ、開発効率を最大化する開発アプローチ。
tool: Flutter, Figma
workflow:
--------------------------------
- step: 1. ワイヤーフレームテーマの適用 (Theme Application)
  details: 開発の初期段階では、`usalingo_04_04`で定義された「ワイヤーフレームテーマ」をアプリケーション全体に適用する。これにより、全ての装飾的要素が排除され、レイアウトと機能配置に集中できる環境を構築する。
--------------------------------
- step: 2. UI骨格の実装 (UI Scaffolding)
  details: Figmaなどで設計された画面レイアウトに基づき、具体的なブロック（ボタン、テキストフィールド、カード等）を配置し、画面全体の構造をコードとして実装する。この段階では、データの表示やボタンの動作はモックデータや空の関数を用いて仮実装する。
--------------------------------
- step: 3. ロジックとデータの統合 (Logic & Data Integration)
  details: UIの骨格が完成した後、実際のビジネスロジック（状態管理、API通信、データベース連携など）を実装し、UIコンポーネントと接続する。
--------------------------------
- step: 4. デザインテーマの適用 (Final Design Application)
  details: 機能実装が完了、または一定の目処が立った段階で、適用するテーマを「ワイヤーフレームテーマ」から「フラットデザインテーマ」などの本番用テーマに切り替える。これにより、機能はそのままに、アプリケーションの見た目を最終的なデザインへと一括で変更する。
```

### **● マイグレーション**

*データベーススキーマの変更を安全かつ再現可能な形で管理・適用するための標準的な開発プロセス。全てのスキーマ変更はこのワークフローに従い、Gitでバージョン管理される。*

```yaml
--------------------------------
WORKFROW: "データベースマイグレーション"
name: データベースマイグレーション (Database Migration)
description: データベースの構造変更をコードとして管理し、開発環境から本番環境へ安全に適用するための標準手順。
tool: Supabase CLI
workflow:
--------------------------------
- step: 1. 変更ファイルの作成 (Creation)
details: 開発者のローカル環境で supabase migration new <migration_name> コマンドを実行し、スキーマ変更内容を記述するための新しいSQLファイルを作成する。
--------------------------------
- step: 2. スキーマ変更の記述 (Implementation)
details: 作成されたSQLファイルに、CREATE TABLE, ALTER TABLE, CREATE INDEX などのSQL文を記述する。
--------------------------------
- step: 3. 開発環境でのテスト (Testing)
details: 開発環境のデータベースに対してマイグレーションを適用 (supabase db push等) し、意図通りにスキーマが変更され、既存機能に影響がないことを確認する。
--------------------------------
- step: 4. バージョン管理へのコミット (Commit)
details: テストが完了したマイグレーションファイルをGitにコミットし、チームにレビューを依頼する。
--------------------------------
- step: 5. 本番環境への適用 (Deployment)
details: レビューで承認された後、CI/CDパイプラインまたは手動で supabase migration up コマンドを実行し、本番環境のデータベースに一連の変更を適用する。
```
