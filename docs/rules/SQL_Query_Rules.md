# Supabase SQLクエリ・マイグレーション統合ルールブック

## 🎯 基本原則

### 1. マイグレーション必須原則
- **全てのデータベース変更はマイグレーションファイルで管理する**
- 直接的なSQL実行（`ALTER TABLE`, `CREATE TABLE`等）は禁止
- 例外: 緊急時の修正（後でマイグレーションファイル化必須）

### 2. 段階的変更原則
- 1つのマイグレーションで1つの変更のみ
- 複雑な変更は複数のマイグレーションに分割
- 依存関係を考慮した順序での実装

### 3. 安全性確保原則
- データ削除を含む変更は事前承認必須
- ロールバック用SQLの提供
- テスト環境での事前検証

## 📁 ファイル命名規則

### SQLクエリファイル（一時的・テスト用）
```
形式: {YYYYMMDD}_{機能名}.sql

例:
20250130_ユーザー設定テーブル作成.sql
20250130_ストレージバケット追加.sql
20250130_インデックス最適化.sql
```

### マイグレーションファイル（本格運用）
```
形式: {番号}_{機能名}_{詳細}.sql

例:
008_add_user_profiles.sql
009_create_learning_progress.sql
010_add_fulltext_search_indexes.sql
```

### 番号管理
- 3桁の連番を使用（008, 009, 010...）
- 既存の最大番号を確認してから次番号を決定
- 番号の重複は絶対禁止

### 理由
- 時系列が明確
- 検索しやすい
- 重複を避けやすい
- 実行順序が分かりやすい

## 🔧 ファイル構造

### SQLクエリファイル用ヘッダー（必須）
```sql
-- ===============================================
-- {機能名} - {詳細説明}
-- ===============================================
-- 作成日: {YYYY-MM-DD}
-- 目的: {何をするためのクエリか}
-- 実行順序: {依存関係がある場合}
-- 注意事項: {重要な注意点があれば}
```

### マイグレーションファイル用テンプレート（必須）
```sql
-- =============================================
-- {機能名}の{操作}
-- =============================================
-- マイグレーションID: {番号}
-- 作成日: {YYYY-MM-DD}
-- 作成者: {AIエージェント名/ユーザー名}
-- 目的: {変更の目的と理由}
-- 依存関係: {前提となるマイグレーション番号}

-- =============================================
-- 1. 変更内容
-- =============================================

-- ここに変更内容を記述

-- =============================================
-- 2. データマイグレーション（必要に応じて）
-- =============================================

-- 既存データの移行処理

-- =============================================
-- 3. マイグレーション記録
-- =============================================

SELECT apply_migration(
    '{番号}',
    '{マイグレーション名}',
    '{詳細説明}',
    NULL, -- checksum (オプション)
    '{ロールバック用SQL}' -- 可能な限り提供
);
```

### セクション分け
```sql
-- ===============================================
-- 1. {セクション名}
-- ===============================================

-- 処理内容

-- ===============================================
-- 2. {次のセクション名}
-- ===============================================
```

### フッター（必須）
```sql
-- ===============================================
-- 完了確認
-- ===============================================
SELECT '処理完了' as status;
```

## 🤖 AIエージェント向けルール

### 変更前の確認事項
1. **現在の最大マイグレーション番号を確認**
   ```sql
   SELECT MAX(migration_id) FROM schema_migrations;
   ```

2. **影響範囲の分析**
   - 既存テーブルへの影響
   - 外部キー制約への影響
   - アプリケーションコードへの影響

3. **ロールバック計画の策定**
   - 変更を取り消す方法
   - データ損失の有無
   - 依存関係の考慮

### マイグレーション作成手順
1. **ファイル名の決定**
   - 次の番号を確認
   - 機能名を明確に表現
   - ファイル名で内容が分かるように

2. **テンプレートの使用**
   - 上記の必須テンプレートを使用
   - 全ての必須項目を記入

3. **テストの実行**
   - テスト環境での事前実行
   - エラーチェック
   - パフォーマンス確認

### 禁止事項
- ❌ 既存マイグレーションの修正
- ❌ 番号の重複使用
- ❌ ロールバック不可能な変更（データ削除等）
- ❌ 複雑な変更の一括実行

## 🗄️ スキーマ変更のルール

### テーブル作成
```sql
-- 既存チェック
CREATE TABLE IF NOT EXISTS {テーブル名} (
    -- カラム定義
);

-- インデックス作成
CREATE INDEX IF NOT EXISTS idx_{テーブル名}_{カラム名} 
ON {テーブル名}({カラム名});
```

### カラム追加
```sql
-- 安全な追加
ALTER TABLE {テーブル名} 
ADD COLUMN IF NOT EXISTS {カラム名} {データ型} DEFAULT {デフォルト値};
```

### データ削除
```sql
-- 削除前の確認
SELECT COUNT(*) FROM {テーブル名} WHERE {条件};

-- 安全な削除（CASCADE確認）
DELETE FROM {テーブル名} WHERE {条件};
```

### 緊急時の対応
```sql
-- 緊急修正の場合（後でマイグレーション化必須）
-- 例: データ破損の修復
UPDATE table_name SET column = 'fixed_value' WHERE condition;

-- 必ず後でマイグレーションファイルを作成
-- 009_emergency_data_fix.sql として記録
```

## 🔒 RLSポリシーのルール

### ポリシー作成パターン
```sql
-- 全ユーザー読み取り可能
CREATE POLICY "{テーブル名}_select_policy" ON {テーブル名}
    FOR SELECT USING (true);

-- 認証ユーザーのみ
CREATE POLICY "{テーブル名}_policy" ON {テーブル名}
    FOR ALL USING (auth.uid() = user_id);
```

## ⚡ パフォーマンス最適化

### インデックス作成
```sql
-- 単一カラムインデックス
CREATE INDEX IF NOT EXISTS idx_{テーブル名}_{カラム名} 
ON {テーブル名}({カラム名});

-- 複合インデックス
CREATE INDEX IF NOT EXISTS idx_{テーブル名}_{カラム1}_{カラム2} 
ON {テーブル名}({カラム1}, {カラム2});
```

## 🚨 エラーハンドリング

### よくあるエラーと対処法

#### 1. マイグレーション重複エラー
```sql
-- エラー: Migration already applied
-- 対処: マイグレーション状態を確認
SELECT * FROM get_migration_status('008');
```

#### 2. 依存関係エラー
```sql
-- エラー: Table does not exist
-- 対処: 依存マイグレーションの実行確認
SELECT migration_id FROM schema_migrations 
WHERE migration_id IN ('001', '002', '003');
```

#### 3. 一般的なエラー対策
```sql
-- 存在チェック
IF EXISTS (SELECT 1 FROM {テーブル名} WHERE {条件}) THEN
    -- 処理
END IF;

-- トランザクション使用
BEGIN;
    -- 処理
COMMIT;
```

```sql

    user_id UUID REFERENCES users(id), -- ユーザーID
    word_id INT REFERENCES words(id),  -- 単語ID
```

## 📊 監視とメンテナンス

### 定期的な確認項目
1. **マイグレーション履歴の確認**
   ```sql
   SELECT * FROM schema_migrations ORDER BY applied_at DESC;
   ```

2. **未適用マイグレーションの確認**
   - 新しいマイグレーションファイルの存在確認
   - 環境間の差分確認

3. **パフォーマンス監視**
   - インデックスの効果測定
   - クエリ実行時間の監視

## ✅ 実行後の確認

### 必須確認クエリ
```sql
-- テーブル作成確認
SELECT table_name FROM information_schema.tables 
WHERE table_schema = 'public' AND table_name = '{テーブル名}';

-- インデックス確認
SELECT indexname FROM pg_indexes 
WHERE tablename = '{テーブル名}';

-- RLS確認
SELECT schemaname, tablename, rowsecurity 
FROM pg_tables WHERE tablename = '{テーブル名}';

-- マイグレーション状態確認
SELECT migration_id, applied_at FROM schema_migrations 
WHERE migration_id = '{番号}';
```
