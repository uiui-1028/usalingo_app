## 🎯 具体的な実装例

### 例1: 新しいテーブルの追加
```sql
-- =============================================
-- ユーザー学習統計テーブルの作成
-- =============================================
-- マイグレーションID: 008
-- 作成日: 2025-01-30
-- 作成者: AIエージェント (GPT-4o)
-- 目的: ユーザーの学習進捗を統計的に分析するためのテーブル追加
-- 依存関係: 001 (基本スキーマ), 006 (タイムスタンプ)

-- =============================================
-- 1. スキーマ変更
-- =============================================

CREATE TABLE public.user_learning_stats (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
    total_words_studied INTEGER DEFAULT 0,
    total_time_minutes INTEGER DEFAULT 0,
    average_accuracy DECIMAL(5,2) DEFAULT 0.00,
    streak_days INTEGER DEFAULT 0,
    last_study_date TIMESTAMPTZ,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- =============================================
-- 2. インデックス作成
-- =============================================

CREATE INDEX idx_user_learning_stats_user_id ON public.user_learning_stats(user_id);
CREATE INDEX idx_user_learning_stats_last_study_date ON public.user_learning_stats(last_study_date);

-- =============================================
-- 3. マイグレーション記録
-- =============================================

SELECT apply_migration(
    '008',
    'User Learning Stats Table',
    'ユーザーの学習統計を管理するテーブルを追加。学習進捗の分析と可視化に使用。',
    NULL,
    'DROP TABLE IF EXISTS public.user_learning_stats CASCADE;'
);
```

### 例2: 既存テーブルの変更
```sql
-- =============================================
-- 単語テーブルに難易度カラムの追加
-- =============================================
-- マイグレーションID: 009
-- 作成日: 2025-01-30
-- 作成者: AIエージェント (GPT-4o)
-- 目的: 単語の難易度を直接管理できるようにするため
-- 依存関係: 001 (基本スキーマ)

-- =============================================
-- 1. スキーマ変更
-- =============================================

-- カラムの追加
ALTER TABLE public.words 
ADD COLUMN difficulty_level INTEGER DEFAULT 1 
CHECK (difficulty_level BETWEEN 1 AND 10);

-- コメントの追加
COMMENT ON COLUMN public.words.difficulty_level IS 
'単語の難易度レベル（1-10、1が最も簡単）';

-- =============================================
-- 2. データマイグレーション
-- =============================================

-- 既存の単語にCEFRレベルに基づいて難易度を設定
UPDATE public.words w
SET difficulty_level = CASE 
    WHEN EXISTS (
        SELECT 1 FROM public.word_meanings wm 
        WHERE wm.word_id = w.id AND wm.cefr_level = 'A1'
    ) THEN 2
    WHEN EXISTS (
        SELECT 1 FROM public.word_meanings wm 
        WHERE wm.word_id = w.id AND wm.cefr_level = 'A2'
    ) THEN 3
    WHEN EXISTS (
        SELECT 1 FROM public.word_meanings wm 
        WHERE wm.word_id = w.id AND wm.cefr_level = 'B1'
    ) THEN 5
    WHEN EXISTS (
        SELECT 1 FROM public.word_meanings wm 
        WHERE wm.word_id = w.id AND wm.cefr_level = 'B2'
    ) THEN 7
    WHEN EXISTS (
        SELECT 1 FROM public.word_meanings wm 
        WHERE wm.word_id = w.id AND wm.cefr_level IN ('C1', 'C2')
    ) THEN 9
    ELSE 1
END;

-- =============================================
-- 3. インデックス作成
-- =============================================

CREATE INDEX idx_words_difficulty_level ON public.words(difficulty_level);

-- =============================================
-- 4. マイグレーション記録
-- =============================================

SELECT apply_migration(
    '009',
    'Add Difficulty Level to Words',
    'wordsテーブルに難易度レベルカラムを追加。CEFRレベルに基づいて既存データも自動設定。',
    NULL,
    'ALTER TABLE public.words DROP COLUMN IF EXISTS difficulty_level CASCADE;'
);
```

## 🚨 エラーハンドリング

### よくあるエラーと対処法

#### 1. テーブルが存在しないエラー
```sql
-- エラー: relation "table_name" does not exist
-- 対処: 依存関係を確認
SELECT migration_id, migration_name 
FROM schema_migrations 
WHERE status = 'applied' 
ORDER BY applied_at;
```

#### 2. カラムが既に存在するエラー
```sql
-- エラー: column "column_name" of relation "table_name" already exists
-- 対処: IF NOT EXISTS を使用
ALTER TABLE public.table_name 
ADD COLUMN IF NOT EXISTS column_name TEXT;
```

#### 3. 外部キー制約エラー
```sql
-- エラー: insert or update on table violates foreign key constraint
-- 対処: 参照先データの存在確認
SELECT COUNT(*) FROM referenced_table WHERE id = reference_value;
```

## 🔍 テスト手順

### 1. 構文チェック
```bash
# SQLファイルの構文チェック
psql -d test_database --single-transaction --set ON_ERROR_STOP=on -f migration_file.sql
```

### 2. 動作確認
```sql
-- マイグレーション適用後の確認
SELECT * FROM get_migration_status('008');

-- テーブル構造の確認
\d new_table_name;

-- データの確認
SELECT COUNT(*) FROM new_table_name;
```

### 3. ロールバックテスト
```sql
-- ロールバックのテスト
SELECT rollback_migration('008');

-- ロールバック後の確認
SELECT * FROM get_migration_status('008');
```

## 📊 パフォーマンス考慮事項

### 1. インデックス作成時の注意
```sql
-- 大きなテーブルへのインデックス作成は時間がかかる場合がある
-- CONCURRENTLY オプションの使用を検討
CREATE INDEX CONCURRENTLY idx_large_table_column 
ON large_table(column_name);
```

### 2. データマイグレーション時の注意
```sql
-- 大量データの更新時はバッチ処理を考慮
UPDATE table_name SET column = new_value 
WHERE id IN (SELECT id FROM table_name WHERE condition LIMIT 1000);
```

## 💡 ベストプラクティス

1. **小さな変更**: 1つのマイグレーションで1つの変更のみ
2. **明確な命名**: ファイル名で内容が分かるように
3. **詳細なコメント**: なぜその変更が必要かを記述
4. **安全なロールバック**: 可能な限りロールバック用SQLを提供
5. **テストの徹底**: 必ずテスト環境で事前確認
