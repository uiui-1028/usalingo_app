# Supabase マイグレーション開発ルール

## 概要
AIエージェントとSupabaseを共同開発する際のマイグレーション管理ルールです。安全で追跡可能な開発を実現します。

---

## 🎯 基本原則

### 1. マイグレーション必須原則
- **全てのデータベース変更はマイグレーションファイルで管理する**
- 直接的なSQL実行（`ALTER TABLE`, `CREATE TABLE`等）は禁止
- 例外: 緊急時の修正（後でマイグレーションファイル化必須）

### 2. 段階的変更原則
- 1つのマイグレーションで1つの変更のみ
- 複雑な変更は複数のマイグレーションに分割
- 依存関係を考慮した順序での実装

### 3. 安全性確保原則
- データ削除を含む変更は事前承認必須
- ロールバック用SQLの提供
- テスト環境での事前検証

---

## 📁 ファイル命名規則

### マイグレーションファイル
```
形式: {番号}_{機能名}_{詳細}.sql
例:
- 008_add_user_profiles.sql
- 009_create_learning_progress.sql
- 010_add_fulltext_search_indexes.sql
```

### 番号管理
- 3桁の連番を使用（008, 009, 010...）
- 既存の最大番号を確認してから次番号を決定
- 番号の重複は絶対禁止

---

## 🔧 マイグレーションファイル構造

### 必須テンプレート
```sql
-- =============================================
-- {機能名}の{操作}
-- =============================================
-- マイグレーションID: {番号}
-- 作成日: {YYYY-MM-DD}
-- 作成者: {AIエージェント名/ユーザー名}
-- 目的: {変更の目的と理由}
-- 依存関係: {前提となるマイグレーション番号}

-- =============================================
-- 1. 変更内容
-- =============================================

-- ここに変更内容を記述

-- =============================================
-- 2. データマイグレーション（必要に応じて）
-- =============================================

-- 既存データの移行処理

-- =============================================
-- 3. マイグレーション記録
-- =============================================

SELECT apply_migration(
    '{番号}',
    '{マイグレーション名}',
    '{詳細説明}',
    NULL, -- checksum (オプション)
    '{ロールバック用SQL}' -- 可能な限り提供
);
```

## 🤖 AIエージェント向けルール

### 変更前の確認事項
1. **現在の最大マイグレーション番号を確認**
   ```sql
   SELECT MAX(migration_id) FROM schema_migrations;
   ```

2. **影響範囲の分析**
   - 既存テーブルへの影響
   - 外部キー制約への影響
   - アプリケーションコードへの影響

3. **ロールバック計画の策定**
   - 変更を取り消す方法
   - データ損失の有無
   - 依存関係の考慮

### マイグレーション作成手順
1. **ファイル名の決定**
   - 次の番号を確認
   - 機能名を明確に表現
   - ファイル名で内容が分かるように

2. **テンプレートの使用**
   - 上記の必須テンプレートを使用
   - 全ての必須項目を記入

3. **テストの実行**
   - テスト環境での事前実行
   - エラーチェック
   - パフォーマンス確認

### 禁止事項
- ❌ 既存マイグレーションの修正
- ❌ 番号の重複使用
- ❌ ロールバック不可能な変更（データ削除等）
- ❌ 複雑な変更の一括実行

## 👥 人間開発者向けルール

### マイグレーション承認プロセス
1. **AIエージェントからの提案**
   - マイグレーションファイルの提出
   - 変更理由の説明
   - 影響範囲の分析結果

2. **人間によるレビュー**
   - 変更内容の妥当性確認
   - ロールバック可能性の確認
   - アプリケーションへの影響評価

3. **承認後の実行**
   - テスト環境での実行
   - 動作確認
   - 本番環境への適用

### 緊急時の対応
```sql
-- 緊急修正の場合（後でマイグレーション化必須）
-- 例: データ破損の修復
UPDATE table_name SET column = 'fixed_value' WHERE condition;

-- 必ず後でマイグレーションファイルを作成
-- 009_emergency_data_fix.sql として記録
```

## 📊 監視とメンテナンス

### 定期的な確認項目
1. **マイグレーション履歴の確認**
   ```sql
   SELECT * FROM schema_migrations ORDER BY applied_at DESC;
   ```

2. **未適用マイグレーションの確認**
   - 新しいマイグレーションファイルの存在確認
   - 環境間の差分確認

3. **パフォーマンス監視**
   - インデックスの効果測定
   - クエリ実行時間の監視

### メンテナンス作業
- 月次でのマイグレーション整理
- 不要なロールバック用SQLの削除
- ドキュメントの更新

## 🚨 エラー対応

### よくあるエラーと対処法

#### 1. マイグレーション重複エラー
```sql
-- エラー: Migration already applied
-- 対処: マイグレーション状態を確認
SELECT * FROM get_migration_status('008');
```

#### 2. 依存関係エラー
```sql
-- エラー: Table does not exist
-- 対処: 依存マイグレーションの実行確認
SELECT migration_id FROM schema_migrations 
WHERE migration_id IN ('001', '002', '003');
```

#### 3. ロールバックエラー
```sql
-- エラー: Rollback failed
-- 対処: 手動でのロールバック実行
-- ロールバック用SQLを手動実行
```
