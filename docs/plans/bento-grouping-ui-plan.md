## 1. 目的

画面上の部品が「一枚の平面にバラバラに並んでいる」状態をやめ、**意味のまとまりごとに枠で囲う**。弁当箱の仕切りのように、どこからどこまでが1つの話題なのかを見た瞬間に分かるようにする（視認性の向上）。

いまの学習タブは、デッキ行のカードと追加ボタンとエラー表示が同じ余白で縦に並んでいるだけで、「デッキ一覧」という群がどこで終わるのかが視覚的に示されていない。ここを直すのが最初の一歩になる。

## 2. 前提

既存の Outline Wireframe デザインシステム（`DesignSystem/`）を土台にする。作り直さない。

- 色は無彩色のみ。色相を持つ色は追加しない。
- 強調は「線幅」と「黒ベタ反転」で行う、という原則は維持する。
- 学習タブと AppShell だけが移行済みで、プロフィール／デザインタブは旧 `AppStyle`（オレンジ・青など色付き）のまま残っている。

## 3. 決めたこと（すり合わせ結果）

| 論点 | 決定 |
|---|---|
| 灰色の濃淡の単位 | **画面の上→下で段階的に濃くする**。上部のグループほど薄く、下部のグループほど濃い |
| 適用範囲 | **学習タブ先行**。プロフィール／デザインタブは今回触らない |
| 入れ子の枠 | **外側のグループ枠を主役にし、中のデッキ行からは枠線を外す**。区切り線と余白で分ける |
| 既存操作 | **維持する**。`List` を残し、左スワイプの書き出し・長押しの並べ替え・削除はそのまま動かす |

## 4. トークン設計

### 4.1 可読性から階調の下限を決める（方針）

**既存の文字色は一切変えない。** そのうえで、いま最も条件の厳しい文字である補助テキスト `subText` `#6B6D71` が、どの段の上でも WCAG AA の本文基準 4.5:1 を満たす範囲だけを階調に使う。

`subText` の相対輝度は 0.1527。コントラスト比 4.5:1 を保つには、下地の相対輝度が 0.862 以上でなければならない。これを sRGB へ戻すと **`#EFEFF0` 付近が最も濃くできる限界**になる。したがって階調は白から `#F0F0F1` までの狭い帯に収める。

### 4.2 面の階調（新規）

段は3つ。上から下へ、この順に使う。

| トークン | 値 | `subText` とのコントラスト比 | 使いどころ |
|---|---|---|---|
| `surface` | `#FFFFFF` | 5.18:1 | 既存。単体のカード、シート |
| `groupL1` | `#FFFFFF` | 5.18:1 | 最上段のグループ |
| `groupL2` | `#F7F7F8` | 4.85:1 | 中段のグループ |
| `groupL3` | `#F0F0F1` | 4.55:1 | 最下段のグループ |

段の指定は View 側に生の色を書かせない。`BentoTone` という列挙（`.l1`〜`.l3`）を通してのみ指定する。

> [!IMPORTANT]
> 濃淡の差は意図的に小さい。**まとまりを分けている主役は枠線であり、階調はその補助**という位置づけにする。ユーザーの指示どおり、可読性を落としてまで濃淡を付けることはしない。実機で差がほとんど見えない場合は、階調をやめて全段 `#FFFFFF` にしても設計として成立する（`BentoTone` の値を変えるだけで済むようにしておく）。

### 4.3 影の扱い

`BentoGroup` は `OffsetShadow` を引数で受け取る。ただしデッキ一覧のように `List` の行背景で枠を描くグループでは、行ごとに背景が切り取られるためハードシャドウが分断されてしまう。学習タブでは**グループの影は使わず**（`shadow: nil`）、枠線と階調だけで面を分ける。フローティングタブバーは行背景ではないので、既存の `.card` の影をそのまま残す。

## 5. 新しい部品

### 5.1 `BentoGroup`（`DesignSystem/Components/BentoGroup.swift`）

まとまりを囲う枠。中身は任意。

```
BentoGroup(title: "デッキ一覧", tone: .l1) {
    // 中身
}
```

- 枠線 `strokeHeavy`（2.0）、角丸 `radiusLarge`（20）、塗りは `tone` の段。
- `title` があれば枠内の左上に `wireFont(.titleS)` で置く。省略可。
- `accessory`（右上の小さい操作、たとえば「編集」）を任意で受け取る。
- 中に置く要素は原則として枠を持たない。区切りは `WireDivider` と `spacingL` の余白で行う。

### 5.2 `BentoRowBackground`（`List` 用）

`List` を残したまま連続した1つの枠に見せるための背景。行ごとに `listRowBackground` として敷き、行の位置（`.top` / `.middle` / `.bottom` / `.single`）に応じて、

- 塗りは段の色、
- 左右の枠線は常に描く、
- 上の枠線と上の角丸は `.top` と `.single` のときだけ、
- 下の枠線と下の角丸は `.bottom` と `.single` のときだけ

を描く。結果として、セクション全体が1つの角丸の枠に見える。行間には `strokeHair` の区切り線を入れる（最終行を除く）。

> [!IMPORTANT]
> この方式を採るのは、`swipeActions` / `onMove` / `onDelete` が `List` の外では使えないため。代償として、**左スワイプ中は枠の左右の線が行と一緒に動く**。並べ替えモードでは行が右へインデントされ、枠の内側の余白が一時的に変わる。これは既知の見た目の妥協点として受け入れる。

## 6. 学習タブの構成

上から順に、3つのまとまりへ分ける。**新しい機能や新しい表示項目は足さない**。いまある要素を囲うだけ。

| 位置 | グループ | 段 | 中身 |
|---|---|---|---|
| 上 | デッキ一覧 | `.l1` | デッキ行（枠なし・区切り線で分割）。0件なら空状態の文言 |
| 中 | 操作 | `.l2` | 「＋ デッキを追加」、編集モード中のみ「編集を終える」 |
| 下 | 通知 | `.l3` | エラーがあるときだけ現れる破線ブロック。エラーがなければグループごと出さない |

加えて `AppShellView` のフローティングタブバーの塗りを `.l3` にする。画面の一番下にある常設の部品なので、階調の一番濃い段に合わせると全体の上下方向の流れが揃う。

デッキ行そのものの変更点は次のとおり。

- `.outlineSurface(...)` を外す。枠線とカード影がなくなる。
- 押下フィードバックが枠に依存しなくなるため、`pressedScale`（0.98）と、押下中の背景を1段濃くする表現へ置き換える（下限は `.l3`。押下中も可読性の範囲から出さない）。
- 文字（デッキ名・「新規 n ・ 復習 n」）と余白（`spacingL`）は変えない。

## 8. 受け入れ条件

1. 学習タブで、デッキ一覧・操作・通知の3つのまとまりがそれぞれ枠で囲まれて見える。
2. 枠の塗りが上から下へ段階的に濃くなっている。
3. デッキ行に枠線がなく、区切り線と余白だけで分かれている。二重枠がどこにもない。
4. 左スワイプの「書き出す」、長押しからの並べ替え、削除が従来どおり動く。
5. デッキ0件のとき、空状態がデッキ一覧グループの中に収まっている（枠の外に浮かない）。
6. エラーがないとき、通知グループが画面に出ていない。
7. 色相を持つ色リテラルが `Features/Learning/` と `Features/Shell/` に増えていない。
8. 文字色トークンは変更されていない。全ての段の上で補助テキストのコントラスト比が 4.5:1 以上。

## 9. 検証

- ロジックには手を入れないため、新しい単体テストは追加しない。既存の `UsalingoIOSTests` が通ることを確認する。
- 見た目は `DesignSystemGallery` のプレビューと、シミュレータでの実機確認で見る。確認する状態は、デッキ0件 / 数件 / 編集モード中 / エラー表示中 の4つ。
- コントラスト比は実装した色の値から計算して確認する（受け入れ条件8）。

## 10. やらないこと

- プロフィールタブ、デザインタブ、学習セッション画面の Bento 化。旧 `AppStyle` の脱色を伴うため、別の作業として切り出す。
- 新しい情報の追加（学習サマリー、統計、グラフなど）。今回は既存要素の再配置だけ。
- ダークモード対応。デザインシステム全体で未定義のまま据え置く。
- `List` を捨てて `ScrollView` へ作り替えること。

## 11. 実施結果（2026-08-30）

- B-1〜B-5 を実装。`xcodebuild build` 成功、`UsalingoIOSTests` 65件すべて通過。
- シミュレータ（iPhone 17 Pro / iOS 26.3）で描画を確認。実際に描かれた色を画面から採取して `#FFFFFF` / `#F7F7F8` / `#F0F0F1` を確認した。文字色トークンは未変更。
- 予想どおり、階調の差は目視ではほとんど分からない。まとまりを分けているのは実質的に枠線である。濃淡を強めたい場合は可読性の限界を超えるため、代わりに枠線の太さや余白で差を付けること。
- **未確認**: デッキ複数件（`.middle` の行）、編集モード、左スワイプ、エラー表示の4状態。シミュレータへの操作権限が未許可のため、画面をタップできず確認できていない。

## 12. 未確認の点

- 段の差は可読性の上限に張り付いているため、実機ではほとんど分からない可能性が高い。その場合は階調を捨てて全段を白にし、枠線だけで分ける。判断は B-4 の実機確認で行う。
- グループの見出し（「デッキ一覧」など）を入れるかどうかは実装後の見た目で判断する余地がある。見出しがあると意味は明確になるが、縦の情報量は増える。
