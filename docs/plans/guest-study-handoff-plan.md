## 1. この計画の目的

ログインなしで学習が回るようになった結果、**ログインしても、それまでの学習記録が引き継がれない**状態が残っている。
ここを塞ぐ。放置すると「ログインすると損をする」構造が固まる。

## 2. なぜ「端末が正・サーバはバックアップ」なのか（案A）

ゲストとログイン後で、カードの識別子が別物である。

| | カードの識別子 |
|---|---|
| ゲスト（ローカル） | 同梱JSONを読むときにアプリが振る連番（`toeic-basic#1` → `1`） |
| ログイン後（サーバ） | `user_card_progress.card_id` = `public.cards.id` |

同梱デッキは `decks` テーブルに無いため、両者を結ぶ対応表が存在しない。
対応表を作る案（単語テキストで突き合わせる / 同梱デッキをDBへ登録する）は、
**U-1（サンプルデッキを正本データへ差し替え）が未確定のうちに作ると、差し替え時に作り直しになる。**

案Aは対応付けを一切必要としない。U-1がどう決まっても壊れない。

### 引き換えに諦めること

- サーバ側で学習進捗を集計・分析できない（バックアップはアプリが読む前提の塊として扱う）
- 1ユーザー1バックアップとし、複数端末の同時利用は今回の対象外とする

将来サーバを正へ移す判断をしたときは、そのときの正本データに対して別途移行を設計する。

## 3. 決めたこと

| # | 決定 |
|---|---|
| G-D1 | 学習の正は端末。サーバは復元用のバックアップだけを持つ |
| G-D2 | バックアップは1ユーザー1件。最後に保存した内容で置き換える |

| G-D5 | バックアップには読み込んだデッキJSONも含める。同梱デッキ以外も復元できるようにする |
| G-D6 | マイグレーションSQLは書くが、本番への適用は行わない |

### スコープ外

サーバ側での進捗集計 / 複数端末の同時利用 / 競合の自動マージ / U-1・U-3・U-4

## 4. チケット分割

### G-1 ローカル進捗の書き出しと取り込み

対象: `Services/LocalStudyDataSource.swift`、`Models/`

- 端末に保存している内容（デッキ一覧、カードID対応表、進捗、タグ、単語編集、読み込み済みデッキJSON）を
  1つの `LocalStudySnapshot` として書き出す／取り込む。
- 取り込みは全置き換えとする。取り込み前の状態は戻せないため、呼び出し側で確認を取る。
- `schemaVersion` を持たせ、知らない版は取り込まずに理由を返す。

**受け入れ条件**

- 書き出したスナップショットを別インスタンスへ取り込むと、デッキ・進捗・タグ・単語編集が一致する
- 読み込みで追加したデッキも復元される
- `schemaVersion` が違うスナップショットは取り込まず、理由の分かるエラーになる

### G-2 バックアップ表のマイグレーション

対象: `supabase/migrations/`

- `public.user_local_study_backups` を追加する（1ユーザー1行、`payload jsonb`）。
- 既存の利用者テーブルと同じ流儀に合わせる: RLSで自分の行だけ、
  退会中はアクセスさせない restrictive ポリシー、`updated_at` トリガー、必要最小限のGRANT。
- 肥大化を防ぐため `payload` に上限を設ける。

**受け入れ条件**

- 他人の行を読めない／書けない
- 退会手続き中のアカウントからは読み書きできない
- 適用はしない。SQLの提示までとする

### G-3 バックアップの自動同期

対象: `Services/`、`App/AppState.swift`、`UsalingoIOSApp.swift`

- `GuestStudyBackupService` を追加し、保存・取得・削除を行う。
- `StudyBackupSyncer` がログイン直後・セッション復元直後・学習内容の変化・背面移行の各時点で自動的に動く（G-D3）。
- 端末に学習記録がないときだけサーバの控えを書き戻す。あるときは端末を正として預け直す（G-D4）。
- ゲストのままなら何もしない。失敗しても知らせず、次の機会に取り直す。記録も残さない。

**受け入れ条件**

- ゲストで学習 → ログイン → アプリのデータを消す → ログイン、で進捗が自動的に戻る
- 端末に学習記録があるときは、ログインしても端末の内容が上書きされない
- 未ログインのままアプリを使ってもクラッシュしない

**やらないこと**

- 利用者にバックアップの操作や判断を求めること（1端末での利用を前提とするため）

### G-4 マイグレーションの適用（**完了**）

状態: **完了**（2026-09-04 本番適用済み）。

#### 2026-09-04 の調査と設計変更

当初 `20260828060000` は、退会手続き中のアカウントを締め出す restrictive ポリシーを持ち、
`public.is_current_user_active()` に依存していた。本番へ適用を試みたところ
`ERROR: 42883: function public.is_current_user_active() does not exist` で失敗した
（トランザクションは巻き戻り、本番に痕跡は残っていない）。
この関数を作る `20260825145625_create_account_deletion_lifecycle.sql` が本番へ未適用だったためである。

そこで退会の設計そのものを見直し、**365日の復元期間をやめて即時削除へ改めた**
（[account-deletion-contract.md](../architecture/account-deletion-contract.md) の選択肢1）。
停止状態が存在しなくなるため、`is_current_user_active()` も restrictive ポリシーも不要になり、
`20260825145625` は丸ごと削除した。`20260828060000` からも該当ポリシーを取り除いた。

結果として G-4 は **`20260828060000` を1本流すだけ**になった。依存する関数はもう無い。

- ステージング環境は存在しない。Supabaseプロジェクトは本番 `Usalingo.app`
  （`udvmzaodsrgwecfybkry`）の1つだけである。
- 本番へ未適用の migration は他にもある（2026-04〜06の数本と `20260821133424`、`20260830090000`）。
  一方で後続の `20260830120000` 以降は適用済みという食い違った状態にある。G-4では触らない。
#### 2026-09-04 の適用結果（**完了**）

1. ローカルで `sh scripts/test-local-db.sh` を実行し、**102件すべて成功**、`db lint` もエラー0。
2. 本番 `Usalingo.app` へ `20260828060000` を適用。表・RLS有効・自分の行だけのポリシー4本・
   `updated_at` トリガー1本を作成し、`anon` からは select 不可、`authenticated` は insert 可を確認。
3. Supabase security advisor に `user_local_study_backups` 起因の指摘は無し。
4. 適用時に自動採番された履歴 `20260904094003` を、リポジトリのファイル名と揃うよう
   `20260828060000` へ書き換えた。

**ローカル環境について（別件の記録）**

Supabase CLI 2.33.9 ではローカルスタックが clean start できなかった
（`20260812055432` が `storage.buckets.public` を参照するが、ローカルの `storage.buckets` が5列しかない）。
CLI を 2.116.0 へ更新して解消した。ただし 2.116.0 は存在しないタグ
`storage-api:fix-search-by-timestamp-sqli` を取りに行くため、
手元の `storage-api:v1.26.0` へ同名タグを付けて回避している。CLI側の不具合であり、
将来のCLI更新で不要になる可能性が高い。

対象: 本番Supabase `Usalingo.app`（`udvmzaodsrgwecfybkry`）

`supabase/migrations/20260828060000_create_user_local_study_backups.sql` は、
リポジトリに入っているだけで**本番へ適用していない**。適用するまで、
アプリの自動バックアップ（G-3）は保存時に失敗し続ける（黙って失敗するため利用者には見えない）。

**やること**

1. ローカルSupabaseを復旧し、`supabase test db` を通す。
2. 本番へ `20260828060000` を適用する。
3. 次の2点を実際に触って確かめる。
   - 自分の行を保存・取得・削除できる
   - 他人の `user_id` の行は読めない／書けない
4. 適用後、ログインしてしばらく学習し、別端末相当の初期状態から自動的に復元されることを確認する。

**受け入れ条件**

- ローカルで pgTAP が通った記録が残っている
- 本番適用後、ゲストで学習 → ログイン → データ削除 → ログイン、で自動的に復元される
- この計画書の状態を完了へ更新する

**やらないこと**

- 検証を飛ばして本番へ直接適用すること
- G-4の範囲外である他の未適用 migration を巻き込むこと
