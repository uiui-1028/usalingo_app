## 1. この計画の目的

ログインなしで学習が回るようになった結果、**ログインしても、それまでの学習記録が引き継がれない**状態が残っている。
ここを塞ぐ。放置すると「ログインすると損をする」構造が固まる。

## 2. なぜ「端末が正・サーバはバックアップ」なのか（案A）

ゲストとログイン後で、カードの識別子が別物である。

| | カードの識別子 |
|---|---|
| ゲスト（ローカル） | 同梱JSONを読むときにアプリが振る連番（`toeic-basic#1` → `1`） |
| ログイン後（サーバ） | `user_card_progress.card_id` = `public.cards.id` |

同梱デッキは `decks` テーブルに無いため、両者を結ぶ対応表が存在しない。
対応表を作る案（単語テキストで突き合わせる / 同梱デッキをDBへ登録する）は、
**U-1（サンプルデッキを正本データへ差し替え）が未確定のうちに作ると、差し替え時に作り直しになる。**

案Aは対応付けを一切必要としない。U-1がどう決まっても壊れない。

### 引き換えに諦めること

- サーバ側で学習進捗を集計・分析できない（バックアップはアプリが読む前提の塊として扱う）
- 1ユーザー1バックアップとし、複数端末の同時利用は今回の対象外とする

将来サーバを正へ移す判断をしたときは、そのときの正本データに対して別途移行を設計する。

### スコープ外

## 4. チケット分割

### G-1 ローカル進捗の書き出しと取り込み

対象: `Services/LocalStudyDataSource.swift`、`Models/`

- 端末に保存している内容（デッキ一覧、カードID対応表、進捗、タグ、単語編集、読み込み済みデッキJSON）を
  1つの `LocalStudySnapshot` として書き出す／取り込む。
- 取り込みは全置き換えとする。取り込み前の状態は戻せないため、呼び出し側で確認を取る。
- `schemaVersion` を持たせ、知らない版は取り込まずに理由を返す。

**受け入れ条件**

- 書き出したスナップショットを別インスタンスへ取り込むと、デッキ・進捗・タグ・単語編集が一致する
- 読み込みで追加したデッキも復元される
- `schemaVersion` が違うスナップショットは取り込まず、理由の分かるエラーになる

### G-2 バックアップ表のマイグレーション

対象: `supabase/migrations/`

- `public.user_local_study_backups` を追加する（1ユーザー1行、`payload jsonb`）。
- 既存の利用者テーブルと同じ流儀に合わせる: RLSで自分の行だけ、
  退会中はアクセスさせない restrictive ポリシー、`updated_at` トリガー、必要最小限のGRANT。
- 肥大化を防ぐため `payload` に上限を設ける。

**受け入れ条件**

- 他人の行を読めない／書けない
- 退会手続き中のアカウントからは読み書きできない
- 適用はしない。SQLの提示までとする

### G-3 バックアップの保存・復元とプロフィールタブの導線

対象: `Services/`、`Features/Profile/ProfileDashboardView.swift`

- `GuestStudyBackupService` を追加し、保存・取得・削除を行う。
- プロフィールタブに「学習記録のバックアップ」を置く。保存日時を表示し、保存と復元を選べるようにする。
- 復元は取り込み前に確認を挟む（G-D3・G-D4）。
- 未ログインのときは、ログインが必要であることを示す。

**受け入れ条件**

- ゲストで学習 → ログイン → 保存 → アプリのデータを消す → ログイン → 復元、で進捗が戻る
- 復元の確認を取り消したとき、端末の内容が変わらない
- 未ログインのままバックアップ操作をしてもクラッシュしない

### G-4 マイグレーションの適用（**保留中**）

状態: **保留**。実施日は未定。着手はユーザーの判断による。

対象: Supabaseのステージング環境と本番環境

G-2 で追加した `supabase/migrations/20260828060000_create_user_local_study_backups.sql` は、
リポジトリに入っているだけで**どの環境にも適用していない**。適用するまで、
アプリのバックアップ機能（G-3）は保存時にエラーになる。

**なぜ保留にしたか**

このSQLは読んで確認しただけで、実際のSupabaseへ流したことがない。
本番へ直接流す前に、同じ構造のステージング環境で挙動を確かめる必要がある。

**やること**

1. ステージング環境へ適用する。
2. 次の3点を実際に触って確かめる。
   - 自分の行を保存・取得・削除できる
   - 他人の `user_id` の行は読めない／書けない
   - 退会手続き中のアカウントからは読み書きできない
3. 問題がなければ本番へ適用する。
4. 適用後、アプリの「学習記録のバックアップ」で保存と復元が通ることを確認する。

**受け入れ条件**

- ステージングで上の3点を確認した記録が残っている
- 本番適用後、ゲストで学習 → ログイン → 保存 → 復元、が通る
- この計画書の状態を完了へ更新する

**やらないこと**

- 検証を飛ばして本番へ直接適用すること
