# 決定｜ゲストを「匿名アカウント」にする

決定日: 2026-09-07

## 決めること

ゲストとログイン利用者で、扱えるデッキも学習記録の置き場所も違っていた。

| | いまのゲスト | いまのログイン利用者 |
|---|---|---|
| 見えるデッキ | 端末に同梱したサンプルJSON | 本番Supabaseの公式デッキ |
| 学習記録の置き場所 | 端末のファイル | `user_card_progress` |
| 引き継ぎ | 会員登録時にバックアップとして保存されるだけ | — |

2026-09-07 に次の2点が要件として決まった。

1. サンプルデッキは機能テスト用であり、本番では使わない。**ゲストも最初から
   本番のデッキを使う**
2. ゲストの学習記録は、**会員登録したときに必ず引き継がれる**

いまの作りではどちらも満たせない。ゲストは未認証のため公式コンテンツを読めず
（[公式コンテンツ契約](../architecture/official-content-contract.md)）、記録も
別の場所にあるため引き継ぎは「移送処理を書く」話になる。どう作り直すかを決める。

## 選択肢

1. `anon` ロールへ公式コンテンツの読み取りをGRANTし、端末の記録をログイン時に
   サーバーへ移送する
2. **ゲストを Supabase の匿名アカウントにする。** 起動時に匿名サインインし、
   会員登録は「その匿名アカウントにメールとパスワードを付ける」操作にする
3. いまの二重構造を維持し、移送処理だけを作り込む

## 決めたこと

**選択肢2を採る。**

理由:

- **引き継ぎが「処理」ではなく「性質」になる。** 匿名のときも会員登録後も
  `user_id` が変わらないため、移送するものが無い。移送処理は必ずどこかで
  取りこぼす。取りこぼしようがない作りを選ぶ。
- **デッキが1系統になる。** 端末のサンプルJSONと本番デッキという二重の正本が
  消え、「ゲストだけ動く／ログインだけ動く」という分岐が要らなくなる。
  今日直した「ログインすると追加ボタンが消える」も、同じ根から出ていた。
- **公式コンテンツ契約を崩さない。** 匿名利用者も `authenticated` なので、
  「未認証は公式コンテンツを読めない」という契約はそのまま保てる。
  選択肢1は契約そのものを変えることになる。

選択肢3は、二重の正本を残したまま処理だけ足すため、今後も同じ種類の不一致が
出続ける。採らない。

## この決定が壊すもの

正直に書く。次の作りは役目を終える。

- 端末の同梱サンプルデッキ（`Resources/SampleDecks/`）— 本番の導線からは外す
- `LocalStudyDataSource` を学習の正本として使う経路
- `user_local_study_backups` と `GuestStudyBackupService`（ゲストの記録を
  預かるための表と処理。記録が最初からサーバーにあれば要らない）
- `AppState.isGuest` の意味。「未ログイン」ではなく「匿名アカウント」に変わる

段階的に外す。詳細は [実行計画](../plans/guest-as-anonymous-account-plan.md)。

## 人の手が要ること

私（AI）が実行できない設定変更がある。

- 本番Supabaseの **Anonymous sign-ins を ON** にする（2026-08-23 の
  [監査](usl-248-auth-configuration-audit.md) 時点では OFF）
- 匿名アカウントは実利用者数と別に増える。放置アカウントの削除方針を決める

## やらないこと

- オフライン対応。匿名サインインには初回だけ通信が要る（M1・M2の対象外）
- 匿名アカウントの複数端末での共有。端末を変えれば別の匿名アカウントになる
- 既存のログイン利用者の記録の作り直し。`user_id` は変わらない
