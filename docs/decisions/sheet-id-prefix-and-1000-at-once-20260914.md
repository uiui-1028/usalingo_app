# 決定｜シートのIDに頭文字を付け、1000語を一度に流す

決定日: 2026-09-14

## 決めること

[教材の正本と単語リスト](content-source-and-word-list-20260907.md) で、教材の正本は
Google Spreadsheet（V5の8シート）になった。そのうえで、次の3点がまだ決まっていなかった。

1. **IDの形。** いまのシートは4桁の数字で、千の位でシートを区別している
   （単語 `1001`、意味 `2001`、例文 `3001`、発音 `4001`）。この形だと、1つのシートに
   入れられるのは999件までになる。1000語を入れると単語IDが `2000` 番台に届き、
   意味IDとぶつかる
2. **足りない項目の置き場。** 活用・発音記号・派生語を、どのシートに入れるか
3. **投入の順番。** 前の決定は「まず50語で通し、実機で確認してから残り950語」だった

## 決めたこと

| 項目 | 決定 |
|---|---|
| シートのID | `<頭文字>-<4桁>`。シートの区別は頭文字が受け持つので、数字は各シート `0001` から始める |
| DBのID | **いまの整数のまま。** 取りこむときに頭文字を外し、数字部分を入れる（`w-0001` → `words.id = 1`） |
| 活用・発音記号・派生語 | **すでにある置き場を使う。** `01_core_senses` に列は足さない |
| コンセプト | `simple` の1種だけ。データは用意済み |
| 投入の順番 | **1000語を一度に流す。** 50語と950語に分けない |

### 頭文字

| シート | 主キー | 形 |
|---|---|---|
| `01_core_words` | `word_id` | `w-0001` |
| `01_core_senses` | `sense_id` | `s-0001` |
| `02_content_concepts` | `concept_id` | `c-0001` |
| `02_content_examples` | `example_id` | `e-0001` |
| `03_audio_pronunciations` | `pronunciation_id` | `p-0001` |
| `03_audio_example_audio` | `example_audio_id` | `a-0001` |
| `04_extra_forms`、`04_extra_relations` | `word_id` | 専用IDなし。`w-` を使う |

参照列（`word_id`、`sense_id`、`concept_id`、`example_id`）にも同じ形を使う。

### 足りない項目の置き場

| 項目 | 置き場 |
|---|---|
| 活用 | `04_extra_forms.forms_json` |
| 発音記号 | `03_audio_pronunciations.ipa` |
| 派生語 | `04_extra_relations.relations_json.derivatives` |

## 理由

**頭文字が付けば、IDを見ただけで行き先のシートが分かる。** `word_id` 列に `s-0003` が
入っていたら、それだけで取りちがえだと分かる。数字だけの形では `2003` が正しい意味IDなのか
入れまちがいなのか、見ても区別できない。

**DBを文字IDにしない。** `words.id` などは整数で、`cards`、`user_card_progress`、
利用者のタグと上書きがその整数を参照している。画像・音声パスのCHECK制約
（[`20260812055432`](../../supabase/migrations/20260812055432_define_official_content_contract.sql)）も、
末尾が数字であることを前提にしている。文字IDにすると、学習記録・カード・アプリのモデルまで
書きかえる大きなmigrationになる。頭文字はシートの中で読みやすくするための印なので、
DBへは持ちこまない。

**活用などの置き場は、V5設計にもうある。** 活用を意味の行に置くと、意味が3つある単語では
同じ活用を3回書くことになり、ずれる元になる。
[`source-database-v5.md`](../content/source-database-v5.md) はもともと、単語に1つだけのものを
単語単位のJSONに置いている。この決定でも、その分け方を変えない。

**50語で先に通す理由が小さくなった。** 前の決定で50語から始めたのは、途中で問題が見つかると
やり直しが1000件になるからだった。いまは1000語のデータがそろっている。取りこみも、全件を
置き換え、失敗したら全体を巻き戻す自動処理として作る（USL-308）。問題が見つかっても、
シートを直してもう一度流せばやり直せる。

## 影響

- 前の決定の「投入の順番」（まず50語、あとで950語）は、この決定で置き換える
- [`source-database-v5.md`](../content/source-database-v5.md) の共通ルールにIDの形を書き足す
- [`official-content-contract.md`](../architecture/official-content-contract.md) のパスの数字は、
  シートのIDではなくDBの整数ID（頭文字を外した数字）である
  - 例文画像・例文音声: 例文ID（`e-`）の数字
  - 単語音声: 発音ID（`p-`）の数字（[USL-283](usl-283-media-delivery.md) のとおり）
- [`milestones.md`](../plans/milestones.md) のM2で「まず50語で一度通す」としていた危険の書き方を変える
- 1つのシートに入れられるのは9999件まで。超える前に桁を増やすかを決める
- Notionの課題を5件から3件にまとめた

| 課題 | 中身 | 統合したもの |
|---|---|---|
| USL-306 | 1000語をシートへ入れ、IDとパスを新しい形にそろえる | 旧USL-306 |
| USL-308 | シート → Supabase の取りこみを作り、状態の食い違いをDBで止める | USL-307 |
| USL-309 | 1000語を流し、実機で最後まで確かめる | USL-310 |

## 決めていないこと

- **採番の固定。** テストデータのうちは変えてよい。実機で学習記録が付いたあとは、
  `w-0001` と `words.id = 1` の対応を変えない。本番前に固定する
- 既存の50語の登録（`1001` などの整数ID）の片付け方。1000語で置き換えるとき（USL-309）に扱う
