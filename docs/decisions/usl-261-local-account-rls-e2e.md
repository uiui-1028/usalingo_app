# USL-261 アカウント管理・RLS ローカルE2E

確認日: 2026-08-28

## 結論

本番から隔離したローカル Supabase で、使い捨ての利用者A・Bと匿名を使い、利用者データのRLS、Authメール、退会、365日保持境界後の最終purgeを一連で確認した。Aの操作と削除はBおよび公式コンテンツへ影響せず、最終purge後はAのAuthレコードとアプリデータが残っていなかった。

## 実行境界

- 実行環境: `project_id=usalingo-local`、API・Mailpit・DBはlocalhostのみ
- Supabase CLI: 2.33.9
- Docker: 29.7.2
- データ: `example.test` のランダム名を持つ合成利用者A・Bだけを使用
- 削除: Aだけを退会させ、Aの保持期限だけを366日経過へ人工更新して最終purge
- 本番 Supabase、実利用者、実メール、画像、音声: 接続・作成・変更・削除なし

## 確認結果

- Aは自分のプロフィールと学習進捗を作成・読取・更新できた。
- AからBのプロフィールは0件に隠れ、Bへの更新・学習進捗削除も反映されなかった。
- 匿名による利用者プロフィール読取と退会Function呼出しは拒否された。
- パスワード回復、再認証、メール変更の要求が成功し、ローカルMailpitへ回復1通、再認証1通、メール変更2通が届いた。
- 回復メールの検証リンクは、許可済みの `usalingo://auth/recovery` へアクセストークン付きで戻った。秘密トークンはログへ出していない。
- 別利用者を指定した退会と誤パスワードによる退会は拒否され、正しいAの退会だけが成功した。
- 退会後のAは再ログインできず、保持中のプロフィールもRLSで0件になった。
- Aだけを保持期限後へ進めた最終purge後、AのAuthレコードは404、アプリ利用者行は0件だった。
- Bのプロフィール・学習進捗と公式コンテンツ件数は、Aの退会前後・purge後で変わらなかった。

## E2Eで見つけて直した不備

- Supabase Authの再認証APIは `GET /auth/v1/reauthenticate` だが、iOSとE2EがPOSTして405になっていたためGETへ修正した。
- パスワード回復の `redirect_to` をJSON本文へ入れていたためローカルsite URLへ戻っていた。クエリ項目へ修正し、アプリ専用URLへの遷移を実リンクで確認した。
