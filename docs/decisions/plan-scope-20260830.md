# 決定｜既存の実行計画書のうち、いま進めないものを止める

決定日: 2026-08-30

## 決めること

`docs/plans/` にある3本の実行計画書には、着手済みの部分と未着手の部分が混ざっている。
どれをいま進め、どれを止めるかが決まっていないため、未着手部分が繰り返し検討の対象に
戻ってきていた。マイルストーンM1・M2を基準に、1件ずつ判定して止めるものを確定する。

## 選択肢

1. 3本とも最後まで完了させてから次へ進む
2. マイルストーンに要るものだけ残し、残りは判定を書いて止める
3. 判定を書かずに放置する（これまでの状態）

## 決めたこと

**選択肢2を採る。** 判定は次のとおり。

| 対象 | 判定 | 内容 |
|---|---|---|
| guest-study-handoff-plan.md G-4 | **続行（M1）** | マイグレーション未適用のあいだ、学習記録のバックアップは保存時にエラーになる。人に配る前に必要。Notion USL-245 が対応する |
| external-package-adoption-plan.md 領域1 | **続行（M1）** | 法務・ライセンス・問い合わせ表示。人に配るなら必要。Notion USL-255 が対応する |
| external-package-adoption-plan.md 領域2 | **続行（M2）** | 画像のディスクキャッシュ。画像が実機へ乗るM2と同時に入れる |
| external-package-adoption-plan.md 領域3 | **延期** | 学習記録のヒートマップとストリーク。M1・M2のどちらにも要らない |
| external-package-adoption-plan.md 領域4 | **延期** | オフライン対応。M1・M2のどちらにも要らない。4-3の双方向同期はもともと対象外 |
| bento-grouping-ui-plan.md B-6 | **中止** | 階調ルールの設計メモ。計画書の4章が同じ内容を持っており、別文書を作る価値がない |

## 理由

- M1（TestFlight配信）とM2（50語の通し）を先に置いた。判定の基準はこの2つに要るかどうかだけにする。
- 領域3と領域4は、どちらも作れば価値はあるが、配信と教材の前に置く理由がない。配ってから、
  実際の利用者の反応で優先順位を決めたほうが判断を誤らない。
- B-6は計画書自身が元々「任意」と書いている。同じ内容が `docs/plans/bento-grouping-ui-plan.md`
  の4章にあり、`docs/architecture/` へ写しても正本が2つになるだけになる。

- `docs/plans/external-package-adoption-plan.md`
- `docs/plans/guest-study-handoff-plan.md`
- Notion `Pro｜Usalingo｜02｜Taskspace`

## 延期したものに残る危険

領域3を延期しても、いまのヒートマップが正しくなるわけではない。
`user_card_progress.last_reviewed_at` はカードごとに最後の1回しか残らないため、
同じ日に複数回復習しても1件にしかならず、前日の記録は上書きで消える。
つまり**画面に出ている過去の学習日は事実と違う**。

配る前に、次のどれかを選ぶ必要がある。この選択は「決定｜v0.1で配るものと配らないものを
決める」で行う。

1. v0.1ではヒートマップと学習日数を表示しない
2. 表示するが「参考値」と明記する
3. 領域3を前倒しして正しくする（M1が遅れる）

## 見直す条件

- 内部テスターへ配信し、その反応を見たとき（領域3・領域4の順番はここで決め直す）
- オフラインで使えないという要望が実際に出たとき（領域4）
- ヒートマップの誤りが利用者に見える形で問題になったとき（領域3を前倒し）
