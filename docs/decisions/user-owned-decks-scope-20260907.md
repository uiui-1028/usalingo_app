# 決定｜個人デッキをM2より先に進める

決定日: 2026-09-07

## 決めること

学習タブの「デッキを追加」がログイン中に出ないことが利用者から見つかった。原因は
アプリではなくDBで、`public.decks` に所有者の列がなく、認証利用者は `select` しか
できないためである（[公式コンテンツ契約](../architecture/official-content-contract.md)）。

この状態差を直す「個人デッキ」は、これまで**やらないと決めてあった**。

- [milestones.md](../plans/milestones.md) M2の「含めないこと」に
  「利用者が自分の単語やデッキを作る機能」がある
- [anki-data-model.md](../architecture/anki-data-model.md) の対象外に
  「ユーザー独自デッキ」がある

この判定を維持するか、変えるかを決める。

## 選択肢

1. 判定を維持し、M2（50語の配信）が終わるまで着手しない
2. 判定を変え、M2より先に個人デッキを進める
3. アプリ側だけ暫定対応し、ログイン中は理由を出して断る

## 決めたこと

**選択肢2を採る。** 個人デッキをM2より先に進める。

理由:

- **状態差そのものが不具合として見えている。** 同じアプリで、ログインすると
  できることが減る。これは機能の不足ではなく、利用者から見れば故障である。
- **配る前に直すほうが安い。** M1でTestFlightへ配ると、この状態差はそのまま
  内部テスターの目に触れる。「ログインするとデッキを追加できない」という報告を
  受けてから直すより、先に直すほうが手数が少ない。
- **DBの土台がM2に効く。** M2は50語を公式デッキとして配る。`decks` の
  所有者の考え方をM2の投入より前に決めておかないと、公式と個人の区別を
  あとから入れることになり、入れ直しの範囲が広がる。
- **公式コンテンツ契約は壊れない。** 所有者列は `owner_id is null` を公式とし、
  公式行への書き込みはRLSで一切許可しない。契約の「公式は読み取り専用」は
  そのまま保つ。

選択肢3は状態差を残す。「見えているのに使えない」は、見えないことより
分かりにくいため採らない。

## 影響する場所

- `docs/plans/milestones.md` — M2の「含めないこと」から外し、着手順に置く
- `docs/architecture/anki-data-model.md` — 対象外の記述を更新する
- `docs/architecture/official-content-contract.md` — 個人デッキの権限を追記する
- `docs/plans/user-owned-decks-plan.md` — 実行計画の正本
- `supabase/migrations/20260907000000_add_user_owned_decks.sql`

## やらないこと

- 個人デッキの共有・公開
- 利用者が新しい**単語**を作ること。単語は公式のまま。個人デッキは
  公式の単語を選んで束ねるだけにする
- JSONの取り込みと書き出しのリモート対応。当面は端末（ゲスト）だけに残す
